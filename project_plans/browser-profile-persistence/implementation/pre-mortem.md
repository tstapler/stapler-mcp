# Pre-mortem: browser-profile-persistence
**Date**: 2026-09-23

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | The plan's own copy-pasteable README example, `~/.stapler-mcp/browser-profile` (ADR-0001, line 93), fails `browser_profile_dir`'s `starts_with('/')` absolute-path check (Task 1.1.1a), because `~` is only expanded by an interactive shell — and the realistic way this env var gets set (an MCP client's JSON `env` config block, not a shell rc file) never runs shell expansion. | Operator copies the README example verbatim, restarts the daemon, and is still re-prompted to log in on every restart. No error surfaces to them — only a rejection line in `daemon.log`, which nothing prompts them to open (see #3). | Change the README/ADR example to a literal absolute path (e.g. `/home/alice/.stapler-mcp/browser-profile`) and add a one-line callout that `~` is not expanded in non-shell env configs. Optionally have `browser_profile_dir` expand a leading `~/` itself before the absolute-path check, so the natural value still works. | P1 |
| 2 | The env var only takes effect for a daemon spawned *after* it's set — it must be present in the actual process environment of whatever spawns the daemon (the MCP client, not the operator's shell), the same footgun this repo already has for `BRAVE_API_KEY`/`STAPLER_MCP_HOME` (README:150-152), but here the failure is fully silent (no per-call error) rather than a visible "search failed" symptom. | Operator sets the var in `~/.zshrc`, the MCP client (spawned from a GUI launcher, not a login shell) never inherits it, `ensure_daemon` auto-spawns the daemon with the var absent, and cookies keep vanishing on every restart with zero error anywhere. | Add a cheap diagnostic surface — e.g. have the `ping` RPC response (or a new lightweight tool) echo the active profile mode (`ephemeral` / `persistent at <path>`) so an operator can positively verify configuration took effect instead of inferring it from cookie behavior after the fact. | P1 |
| 3 | The startup log line and the git/sync-folder credential-exposure warning (Task 1.2.1c) — the specific mitigation the adversarial review required in place of a hard reject — only reach `daemon.log`, a file the detached daemon writes to because it "has no controlling terminal" (README:163) and that operators have no reason to proactively tail. | No observable symptom until the operator happens to open `daemon.log`, or discovers the consequence directly (e.g. notices the profile dir got swept into a `git add -A` in a dotfiles repo). | Surface the warning somewhere an operator will actually see once — e.g. append it to the first `navigate` tool-call response after daemon startup, or write a sentinel/marker file whose mere presence is visible via `ls` — rather than relying solely on a passive log file whose whole design premise is "nobody is watching it." | P1 |
| 4 | `describe_launch_error` (Task 1.2.1g) unconditionally prepends "appears to be in use by another stapler-mcp daemon (SingletonLock)" to *any* `Browser::launch` failure whenever `is_persistent` is true — not just genuine lock collisions — per the plan's own text: it returns the SingletonLock-prefixed message whenever `is_persistent` is `true`, else falls through to `PortError::Other(e.to_string())`, with no branch on the underlying error's actual content. | A real, different failure (profile corrupted by a Chrome auto-update, disk full, Chrome binary missing/crashed) surfaces as a SingletonLock-collision message; operator hunts for a phantom second daemon instead of using the README's actual "delete and let it recreate" remedy. | Only apply the SingletonLock-specific wording when the underlying error's `Display` text actually contains a lock-related substring (e.g. `"SingletonLock"` or the known chromiumoxide/CDP connect-failure pattern); otherwise pass the raw error through unprefixed, same as the ephemeral branch. | P2 |
| 5 | `ensure_daemon` only spawns a new daemon when a ping to the existing one fails — so enabling/changing `STAPLER_MCP_BROWSER_PROFILE_DIR` while a daemon from a prior session is still warm (the common case for a long-lived personal daemon) has zero effect until that daemon is manually found and killed, with nothing telling the operator this is required. | Operator edits their MCP client config, restarts the *client* (not the daemon), calls a browser tool, and is baffled that persistence "isn't working" — the multi-day-old daemon process never re-read the environment. | Add an explicit README line generalizing the existing `STAPLER_MCP_HOME` config-change caveat to cover this var too ("env var changes require killing the running daemon — it does not restart itself"), and/or extend the same diagnostic surface from #2 so `ping` reveals the *active* mode, making a stale daemon detectable without reading logs. | P2 |

## P1 Items (address before implementation)
- [x] #1 — Fixed: ADR-0001's example changed to a literal absolute path with a substitute-your-home-dir note (`decisions/ADR-0001-...md`); `browser_profile_dir` (Task 1.1.1a) now expands a leading `~/`/bare `~` via `EnvPort::home_dir()` as defense in depth, with new tests in Task 1.1.1b and a new Story 1.1.1 acceptance criterion; Task 1.4.1a's README spec updated to require a literal-path example plus a tilde-expansion callout.
- [x] #2 — Fixed: new Story 1.2.3 (Tasks 1.2.3a–1.2.3f) adds `Daemon::set_status_extra` (`crates/core/src/daemon.rs`) so the `ping` response echoes `browser_profile_mode` (`"ephemeral"` / `"persistent at <path>"`), wired from `run_daemon()` (Task 1.2.3e) and asserted against a real daemon in Task 1.2.3f.
- [x] #3 — Fixed: the same Story 1.2.3 mechanism also echoes the git/sync-folder credential-exposure warning as `ping`'s `browser_profile_warning` field (Tasks 1.2.3a–1.2.3c), so it's no longer `daemon.log`-only.
