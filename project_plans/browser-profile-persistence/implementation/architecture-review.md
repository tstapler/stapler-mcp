## Concerns

- [x] **Tasks 1.2.1b/1.2.1c, Tech Debt Disposition table** — `NativeBrowser::launch()` is growing a second and third responsibility, not just a branch. Today the function's whole job is "build one `BrowserConfig` and launch Chrome" (confirmed by reading `browser.rs:338-377`: temp-dir construction → `create_dir_all` → `BrowserConfig::builder()` → `Browser::launch()` → spawn reaper). This plan adds (1) conditional Unix permission-hardening of a credential-store directory (Task 1.2.1b) and (2) diagnostic-message specialization for one specific failure mode, SingletonLock collision (Task 1.2.1c) — both are legitimately separate concerns from "launch Chrome," not just an `Option` branch on the same concern. The plan's Tech Debt Disposition table calls this "Extend as-is," reasoning the change is "additive... no new responsibility beyond its existing job" — that undersells it. Per the `code-architecture-best-practices` skill's Refactor-first / Isolate-via-seam / Extend-as-is priority order, this is the **Isolate via seam** case: pull the two new concerns into small named helper functions (e.g. `fn harden_persistent_dir_permissions(dir: &Path) -> Result<(), PortError>` under `#[cfg(unix)]`, and `fn describe_launch_error(e: impl std::fmt::Display, dir: &Path, is_persistent: bool) -> PortError`) called from `launch()`, rather than inlining a `#[cfg(unix)]` block and a conditional `map_err` closure directly into the function body. **Remediation**: update the Tech Debt Disposition table's disposition from "Extend as-is" to "Isolate via seam," and add the two helper-function extractions as explicit sub-steps of Tasks 1.2.1b/1.2.1c.

  **Resolved**: current `plan.md`'s Tech Debt Disposition table now reads "Isolate via seam," and the two extractions are Tasks 1.2.1e (`harden_persistent_dir_permissions`) and 1.2.1g (`describe_launch_error`).

- [x] **Tasks 1.2.1b/1.2.1c — testability gap (Lens 1, Structural integrity)** — Story 1.2.1's acceptance criteria include concrete Given/When/Then cases for the `0700` permission bit and for the SingletonLock-aware error message, but no unit test is scheduled anywhere in the plan to verify either. The only test that touches this code path is Task 1.3.1a's `#[ignore]`d, real-Chrome integration smoke test — and that test asserts cookie persistence across a restart, not the permission bits or the collision-error message text. As currently planned, both of Story 1.2.1's non-trivial acceptance criteria ship with zero automated coverage. This is the direct payoff of the seam extraction above: once `harden_persistent_dir_permissions` and `describe_launch_error` are standalone functions, each becomes trivially unit-testable without a real Chrome process (a `tempfile::tempdir()` + `std::fs::metadata(...).permissions().mode()` check for the former; a plain string-formatting assertion for the latter). **Remediation**: add unit-test tasks for both extracted helpers alongside Tasks 1.2.1b/1.2.1c, in `crates/native/src/browser.rs`'s own `#[cfg(test)]` module (or wherever this crate's existing unit tests for native-adapter logic live).

  **Resolved**: current `plan.md` adds Tasks 1.2.1d (unit tests for `unsafe_profile_location_reason`), 1.2.1f (unit tests for `harden_persistent_dir_permissions`), and 1.2.1h (unit tests for `describe_launch_error`) — each extracted helper now has dedicated, Chrome-free unit-test coverage.

- [x] **Task 1.1.1a, `paths::browser_profile_dir` — illegal state reachable (Lens 2, parse-at-boundary)** — the resolver only checks non-emptiness (`env.var(...).filter(|v| !v.is_empty())`), but the plan's own documentation contract (Task 1.4.1a's acceptance criteria: "setting the var to a non-empty **absolute** path makes it persistent") promises an absolute-path invariant that nothing in the code enforces. A relative value (e.g. `STAPLER_MCP_BROWSER_PROFILE_DIR=profile`) passes through unchanged into `PathBuf::from` (Task 1.2.2a) and then `create_dir_all` (Task 1.2.1a), silently creating the directory relative to the daemon process's current working directory — which for a background daemon started via `ProcessSpawner::spawn_daemon` (`ports.rs:98-103`, "spawns a detached `--daemon` process... redirecting its stdout/stderr... no controlling terminal once detached") is not something the operator reliably controls or can predict. This is exactly the "Validate, then pass the raw value around" anti-pattern the `type-driven-design` skill's Parse-Don't-Validate principle calls out: the boundary check validates one property (non-empty) but not the property the domain actually depends on (absolute). **Remediation**: extend `browser_profile_dir`'s boundary check to reject (return `None`, with an `eprintln!` warning matching this plan's existing fail-open/log style) or otherwise flag a non-absolute value before it ever reaches `create_dir_all`. Add a fourth case to Task 1.1.1b's unit tests: `should_return_none_for_browser_profile_dir_when_relative_path_given`.

  **Resolved**: current `plan.md`'s Story 1.1.1 (4th acceptance criterion) and Task 1.1.1a specify exactly this absolute-path rejection (`!v.starts_with('/')` → `None` + `eprintln!`), and Task 1.1.1b's unit tests include `should_return_none_for_browser_profile_dir_when_relative_path_given`.

## Nitpicks

- Task 1.2.2a leaves an implementation decision open in its own text ("clone needed... — or restructure to compute the log line first from a borrowed reference, whichever reads cleaner at the actual call site"). Low-stakes (cloning an `Option<PathBuf>` is cheap), but a plan should settle this rather than hand an unresolved "whichever" to the implementer.
- The plan's "Unresolved Questions: None" claim, resting on Story 1.3.1's smoke test "addressing" the chromiumoxide cookie-persistence risk, is slightly optimistic: that test is `#[ignore]`d, and this repo's CI never runs `--ignored` tests (verified: no `--ignored` invocation anywhere under `.github/workflows/`) — consistent with existing precedent for `browser_session.rs`/`docs_index.rs`'s own ignored tests, so not a new gap this plan introduces, but the risk is only addressed if a human remembers to run it manually before relying on the feature. Worth a one-line acknowledgment rather than "None."
