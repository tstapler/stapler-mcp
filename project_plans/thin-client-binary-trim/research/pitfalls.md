# Pitfalls: splitting thin-client + daemon, gating deps behind a default-on feature

Observed repo state (VERIFIED by reading files): `crates/native/Cargo.toml` has `default = ["heavy"]`, `heavy = ["dep:chromiumoxide","dep:fastembed","dep:reqwest","dep:url"]`. `crates/thin-client` (package `stapler-mcp`) uses `default-features = false`; `crates/cli` (package `stapler-mcp-daemon`) uses `features = ["heavy"]`. `crates/thin-client` has no `[lib]`; `tool_schema.rs` uses `#[path = "../src/thin_client.rs"]`. `npm/` contains `bin/stapler-mcp.js`, `package.json`, `test/`. Root `Cargo.toml` has `[profile.release] strip = true`, `[profile.release.package."stapler-mcp"]` (opt-level z, codegen-units 1), and `[profile.release-thin]` (inherits release, lto fat, opt-level z).

## 1. Feature unification (resolver) -- the biggest measurement trap

- Features are unioned per build invocation across every selected package. `cargo build --workspace` selects both `stapler-mcp` (no heavy) and `stapler-mcp-daemon` (heavy); `stapler-mcp-native` is compiled ONCE with `heavy` on, and the thin client links that same unified build. Under resolver 1, and also under resolver 2 for same-target normal deps, the thin client's `default-features = false` is overridden. Result: `--workspace` thin-client binary can contain chromiumoxide/fastembed symbols (dead-code elimination may hide some, not guaranteed), and `cargo tree --workspace` shows heavy deps under the thin client.
- Consequence: every acceptance claim (AC1 `cargo tree`, AC4 size) must use `-p stapler-mcp`, e.g. `cargo tree -e normal -p stapler-mcp -i chromiumoxide` (expect "did not match any packages") and `cargo build --release -p stapler-mcp`. Use `cargo tree -e features -p stapler-mcp -i stapler-mcp-native` to see which features were enabled and by whom.
- AC2 `cargo test --workspace` is fine for correctness but does NOT prove the thin client builds without heavy. Add a CI step `cargo build -p stapler-mcp` (and `cargo check -p stapler-mcp-native --no-default-features`) so a regression is caught.
- Silent regression path: any new dependency of the thin client (or of `stapler-mcp-core`) that itself depends on `stapler-mcp-native` with default features re-enables `heavy` for `-p stapler-mcp`. Guard with a CI assertion: `! cargo tree -e normal -p stapler-mcp | grep -E 'chromiumoxide|fastembed|reqwest'`. Workspace-level `[workspace.dependencies]` entries with `default-features` omitted are a classic cause (member `default-features = false` is ignored if the workspace entry is inherited without it, on older toolchains warns, newer errors) -- verify the native dep is a path dep, not workspace-inherited.
- Dev-dependencies: `-p stapler-mcp` `cargo test` unifies dev-deps too. If thin-client dev-deps ever pull the daemon crate or native-with-heavy, `cargo test -p stapler-mcp` builds a heavy native while `cargo build -p stapler-mcp` does not. Keep dev-deps (currently `tempfile`, `futures`) free of it. Resolver 2 only separates dev-dep features when not building tests, so tests can diverge from the shipped binary.
- Check root `[workspace] resolver = "2"` is set (edition 2021 members do not imply it for a virtual workspace).

## 2. Thin-client integration tests need the daemon binary

- `env!("CARGO_BIN_EXE_<name>")` is only defined for bins of the SAME package as the test. Tests in `crates/cli/tests/*` correctly use `CARGO_BIN_EXE_stapler-mcp-daemon` (verified, 5 occurrences). A test in `crates/thin-client/tests/` cannot reference the daemon that way; it fails to compile.
- AC6 ("auto-start resolves to `stapler-mcp-daemon` in the same directory, verified by integration test") therefore needs one of: (a) put the test in `crates/cli/tests` and use `CARGO_BIN_EXE_stapler-mcp` -- not available either (different package); (b) a test that copies/locates both binaries from `target/<profile>/` via `current_exe()` ancestors (`target/debug/deps/<test>` -> `target/debug/`), which only works if both were built, so run `cargo test --workspace` or `cargo build -p stapler-mcp -p stapler-mcp-daemon` first (plain `cargo test -p stapler-mcp` will NOT build the daemon); (c) an unstable artifact dependency (`-Z bindeps`), not for stable; (d) a unit test of `daemon_exe_path()` against a tempdir containing a fake `stapler-mcp-daemon` file, plus an end-to-end test in `crates/cli` that spawns the daemon via `CARGO_BIN_EXE_stapler-mcp-daemon` with `exe_hint` (already the existing pattern). Recommend (d); document that a true two-binary E2E needs the workspace build.
- Make the test fail loudly, not skip, if the daemon is missing, otherwise CI passes vacuously.
- `daemon_exe_path()` must fall back sensibly when `current_exe()` is a symlink (npm bin shims, Homebrew): use `canonicalize` of `current_exe()` before taking `parent()`, or the sibling lookup resolves to the shim dir and misses the daemon. On Linux `current_exe` reads `/proc/self/exe` (already resolved); on macOS it may not be.

## 3. Bin-name collisions

- Cargo errors (warns for lib/bin doc collisions) when two targets in one workspace produce the same output filename: `cargo build --workspace` would clobber `target/debug/stapler-mcp`. Verified fixed: `crates/cli` bin is now `stapler-mcp-daemon`. Residual traps: (1) package vs. bin naming -- thin client package is `stapler-mcp` and cli package is `stapler-mcp-daemon`, so existing scripts using `cargo build -p stapler-mcp` previously built the daemon+thin-client combined binary and now silently build only the thin client; grep CI, Makefile, release scripts, docs, `.cfgcaddy.yml`, and systemd/launchd units for `-p stapler-mcp`, `target/release/stapler-mcp`, and `--daemon`. (2) `--daemon` flag: old running clients or configs invoking `stapler-mcp --daemon` now hit the thin client; decide whether the thin client rejects it with a clear message or execs the sibling daemon. (3) `Cargo.lock` package rename churn; commit it. (4) Debug-info side files (`.pdb`/`.dSYM`) and `cargo install --path` of two bins from different packages: `cargo install` needs both `--path crates/thin-client` and `--path crates/cli`.
- `rust-analyzer`/`cargo run` ambiguity: `cargo run` at workspace root with two bin packages errors "could not determine which binary to run"; set `default-run` or document `-p`.

## 4. `#[path]` includes in tests

- `#[path = "../src/thin_client.rs"]` compiles the file a second time as a module of the test crate. Pitfalls: `crate::` paths inside the included file resolve against the test crate, not the bin (breaks if the file uses `crate::other_module`); dead-code warnings for everything the test doesn't call (needs `#![allow(dead_code)]` or fails clippy `-D warnings`); `#[cfg(test)]` items inside the file are enabled in the test crate only when the test harness crate is compiled with cfg(test), which it is, but `#[cfg(test)]` accessors like `registered_tools()` (thin_client.rs ~line 463) then exist in the test copy but NOT in the real bin -- fine, but a refactor that moves them out of `cfg(test)` leaves dead code in the shipped binary.
- Path is relative to the including file's directory for non-`mod.rs`, and for a test file in `tests/` it resolves relative to `tests/`; the move to `crates/thin-client/tests/` already uses `../src/` (verified), correct. Any other file the included module `mod`-includes would need its own `#[path]`.
- Cleaner alternative: add `[lib]` (`src/lib.rs` holding `thin_client`) and keep `main.rs` tiny. Costs: public surface and `pub(crate)` visibility changes; benefits: no double compilation, normal `use stapler_mcp::...`. Size is unaffected since the bin links the rlib with LTO. Only do this if `#[path]` causes friction; plan currently accepts `#[path]`.
- Rebuild trigger: Cargo tracks `#[path]` dependencies via dep-info, so edits to `src/thin_client.rs` do rebuild the test. OK.

## 5. Tests inside gated modules

- Modules gated by `#[cfg(feature = "heavy")]` in `crates/native/src` (`ax`, `browser`, `embed`, `http`) have their `#[cfg(test)]` unit tests silently removed under `--no-default-features`. Conversely `cargo test -p stapler-mcp-native` (default on) runs them, while `cargo test -p stapler-mcp-native --no-default-features` runs fewer; the number of tests will drop and nothing flags it. Record expected counts per config (derive with `cargo test ... -- --list | grep -c ': test$'`).
- Un-gated modules (`env`, `fs`, `lock`, `sleep`, `spawn`, others) must not `use` anything from gated ones. Check `use crate::http::...`/`crate::embed::...` in non-gated files, and non-gated `pub use` lines. Also check `[dev-dependencies]` of native: if tests in ungated modules use `reqwest`/`url` (now `optional`), `--no-default-features` fails to compile tests. `dep:` optional deps are not available to test code unless also listed as dev-dependencies or the code is gated.
- Integration tests in `crates/native/tests/` that import `NativeBrowser`/`NativeHttp` need `#![cfg(feature = "heavy")]` at file top or `[[test]] required-features = ["heavy"]`; otherwise `cargo test -p stapler-mcp-native --no-default-features` fails to compile.
- Doc-tests in gated items likewise vanish/ fail; gate with the item.
- Feature-gate `cfg` typos are silent: `#[cfg(feature = "heavey")]` compiles to nothing. Newer rustc `unexpected_cfgs` lint catches this; keep it enabled (`[lints.rust] unexpected_cfgs`).

## 6. clippy `-D warnings` under `--no-default-features`

- Imports, helper fns, constants, and error variants used only by gated code become `unused_imports`/`dead_code` in the no-heavy build. These pass `cargo clippy` with defaults and only fail under `cargo clippy -p stapler-mcp-native --no-default-features -- -D warnings`. Run both configurations in CI (default and `--no-default-features`, `--all-targets` for each).
- Error enums with `#[from] reqwest::Error`/chromiumoxide variants must be gated per-variant (`#[cfg(feature = "heavy")]`), including their `match` arms and `From` impls; otherwise the build fails, and un-gated `thiserror` variants of removed types change the public API per feature (additive-feature rule violated: a default-off feature must only add, and here default-OFF removes; consumers matching exhaustively break). Prefer stringly or core-defined error types at the boundary.
- `Cargo.toml` `heavy` also gates `url`; if ungated code parses URLs it breaks -- grep `url::` outside gated modules.
- Do clippy with `-p`, not `--workspace` (see section 1), otherwise heavy is unified on and the no-heavy configuration never gets linted.
- The `lib.rs` `pub use` re-exports are gated individually (verified); also gate any `pub type`/trait impls that name the gated types (e.g. an `impl Ports for ...` aggregate struct).

## 7. npm package is WASM -- what "bundle both binaries" means

- Verified: `npm/` has `bin/stapler-mcp.js`, `package.json` (name `stapler-mcp`, `bin`, `files: ["bin", ...]`), `test/`. The repo also has `crates/wasm` with Node glue (per the `js-playwright-wasm-glue` skill), so the npm package runs the WASM build in Node, not a native binary. There is no native executable in the package today; `stapler-mcp-daemon` (chromiumoxide, fastembed/ONNX, native sockets) cannot meaningfully be compiled to WASM.
- So AC7 as written ("bundles both `stapler-mcp` and `stapler-mcp-daemon`") is ambiguous. Realistic readings, with cost:
  1. No change: npm continues to ship WASM only; AC7 is N/A. Confirm by reading `npm/package.json` `files` and `bin/stapler-mcp.js` (not yet read in full by this pass: UNVERIFIED beyond the first lines).
  2. Ship prebuilt native binaries per platform via the esbuild/biome pattern: `optionalDependencies` on `@scope/stapler-mcp-<os>-<arch>` packages (each with `os`/`cpu` fields containing both executables, exec bit preserved) and a JS launcher that `require.resolve`s the right one. Needs a release CI matrix (linux x64/arm64, darwin x64/arm64, windows if supported), signing/notarization on macOS, and `npm pack` checks that file modes survive (npm strips none, but zip/CI artifact steps can drop +x).
  3. Postinstall download of GitHub release assets: simpler, but breaks with `--ignore-scripts`, offline installs, and corporate proxies; verify checksums.
  Either 2 or 3 must place both binaries in the SAME directory so `daemon_exe_path()` sibling lookup works; with option 2 the JS launcher must exec the native thin client directly (not through a shim that moves it) or `current_exe()` canonicalization must handle it.
- Do not hand-wave AC7 as done by adding a `files` entry that points at nonexistent binaries; add a `npm pack --dry-run` check listing both files.

## 8. Stale daemon after upgrade

- The daemon is long-lived and shared across ~30 sessions. After an upgrade, the new thin client connects to the socket of the OLD daemon (old binary, possibly deleted/replaced on disk; Linux keeps running the unlinked inode). `ensure_daemon` sees a live socket and never starts the new one. Symptoms: new tool added to the thin client schema but daemon returns "unknown method"; wire-protocol mismatch (serde errors); old behaviour persists until reboot.
- Mitigations, cheapest first: (a) a handshake: daemon `ping` returns `{version, build_id}` (daemon_ping.rs exists, so a ping path is there); thin client compares with its own `CARGO_PKG_VERSION` (workspace version is `0.1.0` and does not change per build; use a build hash or content hash of the sibling daemon, otherwise dev rebuilds are never detected); (b) on mismatch the thin client sends a `shutdown`/`restart` request, waits for the socket to close, then `ensure_daemon` respawns; guard with the existing lock (`NativeLock`) so 30 sessions do not stampede; (c) daemon exits when its own executable changes (poll `/proc/self/exe` link target `(deleted)` or mtime); (d) make the socket path version-keyed (`daemon-<version>.sock`) so versions coexist, at the cost of leaked old daemons. Each approach disrupts in-flight browser sessions owned by the old daemon; decide policy and document it.
- Interaction with the split: thin client and daemon are now separately versioned on disk. A partial upgrade (npm/brew replaces only one file, or the daemon sibling is missing) is possible; `daemon_exe_path()` should return a clear error "stapler-mcp-daemon not found next to <path>" rather than a spawn ENOENT hidden behind a retry loop. Also consider the reverse skew: old thin clients (already-running sessions) talking to a new daemon, so keep wire changes additive across at least one version.
- Out of scope per requirements (daemon behaviour "not modified") -- a version handshake edits the daemon. Flag this to the owner; the requirement "Modifying the daemon binary" is a non-goal, so this is a follow-up or needs the constraint relaxed.

## 9. Measuring binary size fairly

Baseline: stripped pre-split `stapler-mcp` = 48,517,136 bytes. Post-split: release thin client 3,657,192 (-92.5%); `release-thin` 2,733,624 (-94.4%). Both exceed the 20% bar by a wide margin (recomputed: 3,657,192/48,517,136 = 0.0754; 2,733,624/48,517,136 = 0.0563). Fairness traps:
- Compare like with like: the baseline must be built with the SAME toolchain, target triple, `strip`, and profile as the candidate. A baseline built from the pre-split commit with `--release` (strip = true, no LTO, opt-level 3) vs. a candidate with opt-level z conflates two effects. Report three numbers: (i) post-split, same profile as baseline (isolates the dependency cut; the honest AC4 number), (ii) post-split with the per-package override, (iii) `release-thin`.
- `[profile.release.package."stapler-mcp"]` only sets opt-level/codegen-units for that ONE package's own code; dependencies (tokio, rmcp, serde) are separate packages and stay at opt-level 3 unless overridden with `[profile.release.package."*"]`. `lto` cannot be set per package (verified by the comment in root Cargo.toml), so AC3's `lto = "fat"` is only met by the separate `release-thin` profile; the plain `--release` binary (3,657,192) is NOT fat-LTO. Be explicit that AC3 is satisfied via a named profile, and that the shipped artifact must be built with `--profile release-thin` for the 2.73 MB number. Release scripts and npm/brew packaging must actually pass that flag, and the output lands in `target/release-thin/`, not `target/release/` (sibling-lookup test and packaging paths must account for this).
- Measure with `-p stapler-mcp` (section 1), clean target dir or at least `cargo clean -p`, and `strip`'d output via `ls -l`/`stat -c %s`; use `wc -c`. Also record `cargo bloat --release -p stapler-mcp --crates` (or `size -A`) to attribute remaining bytes; also compare `.text` since stripping already removes symbols. Do not compare a debug build.
- Compressed vs on-disk size: if shipped in npm/tar, report the gzip size too.
- Do not infer an attack-surface win from size alone: check symbol absence directly, e.g. `strings`/`nm` on an unstripped build for `chromiumoxide`, `fastembed`, `ort`, `reqwest`, `hyper` (the thin client still talks to the daemon over a Unix socket, so tokio and rmcp stay). `cargo tree -e normal -p stapler-mcp` (AC1) is the primary, deterministic evidence; also check `openssl`/`rustls` absence since reqwest was the only TLS consumer.
- Runtime: size is not RSS (requirements already say RSS ~4 MB is mostly unchanged); sample with `ps -o rss` on ~N idle processes before/after if a RSS claim is ever made. Build-time claims (daemon LTO cost) should be timed, not asserted (`cargo build --timings`).
- Reproducibility: record `rustc -V`, `Cargo.lock` hash, target triple and commit SHA next to the numbers; the 48,517,136 baseline is only reproducible if the pre-split commit (`571450c`'s parent state or `main`) is rebuilt; store the exact commit.
- Linux musl vs glibc and macOS differ in size; the quoted numbers are for the host (Linux, glibc). Say so.

1. `cargo tree -e normal -p stapler-mcp | grep -Ec 'chromiumoxide|fastembed|reqwest'` -> 0

6. `npm pack --dry-run` content assertion matching the AC7 decision.
