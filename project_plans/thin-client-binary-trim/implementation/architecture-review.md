## Concerns
- [ ] Story 1.1.2 / Story 1.1.1 / Story 3.1.2 (feature unification is the one structural weakness) — `heavy` is a Cargo feature, and `Cargo.toml` `default-members` lists both `crates/cli` (`features = ["heavy"]`) and `crates/thin-client`. Every plain `cargo build`, `cargo test` and `cargo clippy --workspace` therefore links `chromiumoxide`/`fastembed` into the debug thin client. The AC1 guarantee holds only for `-p stapler-mcp` invoked alone. The plan documents this and gates it in CI, but the gate covers only the one invocation shape and relies on humans following README rules. AC5 mandates the feature, so the plan cannot drop it. Recommendation: (a) keep the script gate, and also have it assert `cargo tree -e features -p stapler-mcp -i stapler-mcp-native` lacks `heavy` (already in Task 3.1.1c; move it into the script); (b) record in an ADR that a separate light crate (adapters without the feature) would remove the hazard by construction, and defer it only because AC5 names the feature; (c) make the CI size gate build with `-p stapler-mcp` alone, exactly as the release does.
- [ ] Task 2.1.1a / Task 2.1.1b (SRP, and a latent footgun) — daemon discovery (`DAEMON_BIN`, `sibling_daemon_path`, `daemon_exe_path`), now with canonicalization, error-message policy and `pub(crate)` exports, is added to `thin_client.rs`, a roughly 500-line file of rmcp tool handlers. `main.rs` then imports it from there for the exec path. The plan also protects against `exe_hint = None` (which makes `NativeSpawner` spawn another thin client, verified at `crates/native/src/spawn.rs:11-15`) only with a comment. Recommendation: put the discovery in its own small module `crates/thin-client/src/daemon_locator.rs`. It exports one function, `locate_daemon(current_exe: Option<&Path>) -> PathBuf`, used by both `call_daemon` and `main`. Optionally add a thin-client-local `SiblingDaemonSpawner` wrapper that implements `ProcessSpawner` and always supplies the hint, so the `None` trap cannot be reached by construction. This also keeps the unit tests out of the `#[path]`-included file that `tests/tool_schema.rs` compiles a second time.
- [ ] Story 3.2.2 / AC7 / ADR-003 (requirements deviation still open) — AC7 reads "`npm/` packaging bundles both `stapler-mcp` and `stapler-mcp-daemon`". Verified: `npm/package.json` has `"files": ["bin","pkg"]` and is a WASM package (`npm/bin/stapler-mcp.js`, no native binary). The plan satisfies AC7 only through reinterpretation (ADR-003 option 1, status Proposed) and header status is still "Ready for implementation". It is flagged honestly, so this is not a blocker, but AC7 cannot be called met without the owner's decision. Recommendation: do not report AC7 as met in the PR; state it as "interpreted, pending owner decision", and have the Phase 7 ship step block on ADR-003 moving to Accepted.
- [ ] Story 1.1.4 / ADR-001 (daemon artifact change versus non-goal) — `[profile.release] strip = true` is workspace-wide, so the daemon's release artifact also changes (stripped). Requirements non-goal: "Modifying the daemon binary". AC3 asks for `lto = "fat"` via `[profile.release.package."stapler-mcp"]`; Cargo rejects `lto` there, so the plan substitutes `release-thin` (ADR-001). The deviation is recorded, but the strip side effect on the daemon is not listed in ADR-001. Recommendation: add one line to ADR-001 saying that the daemon is now stripped and why that is acceptable (or scope strip to `release-thin` plus the per-package override if the owner objects). Keep both owner questions in the PR body.
- [ ] Story 2.1.2 / Task 2.1.2b (testability, hidden build-order coupling) — `crates/cli/tests/thin_exec.rs` needs the `stapler-mcp` binary, which Cargo does not build for `cargo test -p stapler-mcp-daemon` (a dev-dependency on the thin client is also ruled out, correctly, for feature isolation). The test fails with a helpful message when the binary is absent, but a stale `target/debug/stapler-mcp` from an older build would pass silently against old behavior. Recommendation: compare mtimes (or have the test run `cargo build -p stapler-mcp` first) so a stale sibling fails; CI already builds the workspace first. Keep the fake-daemon test (Task 2.1.2a) as the primary isolated proof of AC6.
- [ ] Task 2.2.1b (3) (trial that cannot win) — the plan trials gating tokio `fs`, but ungated `crates/native/src/fs.rs` (`NativeFs`) calls `tokio::fs::{create_dir_all,write,rename,read,remove_file}` and `spawn.rs` uses std `process`. Verified by grep. Dropping the tokio `fs` feature would break the ungated build, so the trial is foregone. Recommendation: remove trial (3), or reduce it to a one-line check. The `rmcp default-features = false` and `panic = "abort"` trials remain valid; for `panic = "abort"`, the thin client is built as a bin, so confirm tests are not run under `release-thin`.

## Nitpicks
- Task 1.1.1c premise is partly stale: `crates/native/tests/` does not exist, and the ungated modules (`env`, `fs`, `lock`, `sleep`, `socket`, `spawn`) import only `stapler_mcp_core`, std, tokio and libc (verified), so the audit is mostly a confirm-by-`cargo clippy --no-default-features` step. Shrink it to that plus the `--list` test counts.
- Task 2.1.1b: use `std::env::args_os()` for the `--daemon` check. `std::env::args()` panics on non-UTF-8 arguments before the launch decision. Also mark the exec path `#[cfg(unix)]` or note that the crate is Unix-only (it already depends on Unix sockets via `stapler-mcp-native`).
- Task 2.1.1a: `EnsureOptions.exe_hint` is `Option<String>`, so a non-UTF-8 install path is lossily converted via `to_string_lossy`. Acceptable, but worth a comment on the single conversion point.
- Task 2.1.1a: canonicalizing `current_exe()` resolves symlinks to the real directory. A layout where the two names are symlinks in one directory pointing at different real directories would then fail the sibling lookup. Consider trying the un-canonicalized sibling first, then the canonical one. On Linux `current_exe()` is already resolved, so the macOS case is the only behavior change (INFERRED, as the plan says).
- Story 3.1.2: a `release-thin` fat-LTO build on every PR is a CI cost. Consider a path filter (`crates/**`, `Cargo.toml`, `Cargo.lock`, `scripts/check-thin-client.sh`) for the size-gate step.
- The plan's "DONE" tasks are unverified until Story 3.1.1 runs, and the status line says so. Keep that sequencing: do not build later waves on DONE items until Task 3.1.1b/c pass.
- Pattern Decisions are well chosen (functional core for discovery, sum type `LaunchMode`, executable gate script); no pattern is over-applied.
