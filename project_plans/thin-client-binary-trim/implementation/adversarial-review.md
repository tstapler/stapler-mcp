# Adversarial Review: thin-client-binary-trim

**Date**: 2026-10-18
**Verdict**: CONCERNS

Checked against the working tree: `Cargo.toml`, `crates/thin-client/{Cargo.toml,src/main.rs,src/thin_client.rs}`, `crates/native/{Cargo.toml,src/lib.rs,src/spawn.rs}`, `crates/cli/src/main.rs`, `.github/workflows/ci.yml`, `npm/package.json`. `cargo tree -e normal -p stapler-mcp` in the current tree shows none of chromiumoxide/fastembed/reqwest/hyper/ort/rustls (VERIFIED by running it; only `url` appears, which is not on the denylist). Nothing found that must stop implementation.

## Blockers
None.

## Concerns
- [ ] **AC7 is not met as written, and the plan's reading is still "Proposed"** — `requirements.md` AC7 says `npm/` bundles both `stapler-mcp` and `stapler-mcp-daemon`. `npm/package.json` is a WASM-only package (`files: ["bin","pkg"]`, `bin/stapler-mcp.js`, no native binary), and Story 3.2.2 only verifies "no regression". This is a deliberate requirement downgrade (ADR-003). Get Tyler's decision before the PR is opened (not just before 3.2.2b), and word the PR as "AC7 reinterpreted", not "AC7 done".
- [ ] **The size gate cannot catch the regressions it is meant to catch** — Story 3.1.2 ceilings the thin client at 38.8 MB while the measured size is 2.73 MB (~14x headroom). Re-adding `rmcp` extras, `reqwest` or `ort` would not necessarily cross it. The denylist is the real gate. Set the ceiling relative to the current measurement (e.g. 4-5 MB, with a comment) or keep the 20% AC4 check as a one-time PR measurement and make the CI ceiling a tight regression bound.
- [ ] **Denylist is incomplete as a fitness function** — it lists exact crate names but omits `url`, `tokio-native-tls`, `openssl`, `native-tls`, `h2`, `onnxruntime`-related crates. `url` already appears in the thin client's graph (via another dependency, not `heavy`), so it cannot go on the list. Prefer asserting `cargo tree -e features -i stapler-mcp-native` shows no `heavy` feature, in addition to names. The plan has this check only in Task 3.1.1c (manual), not in `scripts/check-thin-client.sh`; move it into the script.
- [ ] **"Daemon unchanged" is slightly untrue** — root `[profile.release] strip = true` changes the daemon's release artifact too (stripped), and `[profile.release.package."stapler-mcp"]` is scoped by package name, so any rename silently loses the tuning. The requirement "Modifying the daemon binary" is a non-goal; strip is benign, but say so in ADR-001 and the PR. Add a script assertion that the per-package override still matches an existing package name (a typo is silently accepted by Cargo).
- [ ] **Feature unification guard exists only in docs and CI script** — `cargo build`/`cargo run`/`cargo install` from the workspace root with default-members unify features and link heavy into the dev thin client, and the new `crates/cli/tests/thin_exec.rs` relies on that unified debug binary. The release path is guarded; the dev path is not. Acceptable, but then README (3.2.1b) must state it prominently and the script should build with `-p stapler-mcp` alone (it does); also add a `[workspace]` comment or `Makefile` target so the safe command is discoverable.
- [ ] **Cold fat-LTO build in the hot CI job** — Task 3.1.2b runs `scripts/check-thin-client.sh` (a `release-thin` build) in the same `native` job after `cargo build --workspace` and `cargo test --workspace`. Full fat LTO plus `codegen-units=1` on rmcp/tokio is slower than debug and is not covered by `rust-cache` for the new profile on the first run. Put the gate in its own job (parallel, so it does not lengthen the PR critical path) and note the expected duration.
- [ ] **Legacy `--daemon` exec has an untested interaction with the spawner** — ADR-002 execs the sibling on any argv containing `--daemon`. The daemon accepts and ignores args (`crates/cli/src/main.rs:26`), so extra flags are harmless today, but the AC says argv is forwarded verbatim (`["--daemon","--flag-x"]`). A future daemon with strict arg parsing would break old service units. Low probability; record the assumption in the code comment. Also state what happens when `stapler-mcp --daemon` runs under a service manager with a minimal `PATH` and the sibling is absent (exit 127 is specified; good, but there is no restart-loop note).
- [ ] **Stale-daemon-after-upgrade left unmitigated** — after upgrading, a running pre-split combined daemon holds the lock and socket; the new thin client talks to it and the new `stapler-mcp-daemon` never starts. Recorded as a follow-up, but a cheap doc-only mitigation (README/PR note: "restart the daemon after upgrade", with the exact command) is within scope and not planned in 3.2.1.
- [ ] **No CI coverage for macOS behavior** — Task 2.1.1a canonicalization is justified by a macOS `current_exe` claim marked INFERRED, and the user's work machine is macOS. CI is ubuntu only. Keep the canonicalization (it is harmless on Linux) but add the symlink layout test to the Linux integration test so it is at least exercised, and call out the macOS unverified status in the PR.
