# Pre-mortem: credential-vault
**Date**: 2026-09-08

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | Redaction only scrubs the MCP/AxSnapshot transport; the secret is still written in the clear into the live page DOM via `this.value = text`, so any JS already running on that page (site-side analytics, an injected/XSS script, a compromised third-party widget on the exact-matched domain) can read or exfiltrate it the instant it's typed — the whole feature's threat model (`architecture.md`, ADR-002) analyzes domain-spoofing but never the page's own script having DOM access to what was just typed. | A credential typed via `type_secret` on a real, exact-host-matched but XSS'd or third-party-widget-laden page shows up somewhere it shouldn't (a beacon/analytics call, a support-chat DOM scrape) with no daemon-side error, log anomaly, or failed acceptance test — the feature reports 100% green on every Success Metric while the actual secret still left the machine. | Add an explicit, written scope statement to `requirements.md`/`plan.md`: "never appears in the MCP transport" is not "never leaves the machine" — the live DOM is inherently trusted once a value is typed, matching every real password manager's autofill exposure. State this as an accepted, named residual risk (not a silent gap) and consider a Rabbit-Hole-style guidance note steering the LLM away from typing into third-party/embedded widgets it doesn't recognize as the login provider itself. | P1 |
| 2 | `pitfalls.md` §1d names the exact design rule ("minimize owned buffers the secret passes through... ideally one `Vec<u8>`... zeroized itself after conversion") but the plan's actual tasks don't implement it: `ProcessOutput` (Task 3.1.1a, plan.md:766-772) is a plain `struct { stdout: Vec<u8>, ... }` with no zeroizing `Drop`, and Task 3.2.1b builds `SecretValue::new(String::from_utf8_lossy(...).into_owned())` — `.into_owned()` on the common (valid-UTF-8) path always allocates a fresh copy, leaving both the original `ProcessOutput.stdout` buffer and the intermediate `Cow` holding the plaintext secret with an ordinary (non-zeroizing) drop. | Nothing observable at runtime — this is a memory-forensics-only gap. First real symptom would be a security audit, `/proc/<pid>/mem` inspection, or a crash/core-dump review (post-incident) finding plaintext credentials in daemon heap memory well after the "resolved" call returned, contradicting the regulated NFR's implied guarantee. | Add a task under Epic 3.1/3.2: make `ProcessOutput.stdout` a `Zeroizing<Vec<u8>>` (or zeroize it explicitly immediately after the one-time move into `SecretValue`) for any path known to carry vault output, and change Task 3.2.1b to avoid `from_utf8_lossy(...).into_owned()` in favor of a single validated move into the `Zeroizing<String>` with the source buffer wiped right after. Add a unit test asserting the intermediate buffer is zeroed (or at minimum a code-review checklist item), since this can't be caught by a functional test. | P2 |
| 3 | The native adapter shells out to whatever `op` binary is resolved on `PATH` (Task 3.1.1b) — unlike every other native dependency in this codebase (`chromiumoxide`, `playwright-core`), the 1Password CLI's version is not pinned or verified anywhere in the plan. `op`'s stderr text is pattern-matched verbatim (Task 3.2.4a) against today's exact wording. | Weeks or months after ship, an unrelated `brew upgrade`/OS package update bumps `op` and changes its unauthenticated/rate-limited error wording; `CredentialUnauthenticated`/`CredentialRateLimited` silently stop matching and every such failure falls through to the generic `format!("type secret for {domain}: {other}")` wrap — the LLM (and user) gets a useless generic error instead of the actionable "run `op signin`"/"retry after Ns" message, right when the vault is actually broken. | Log (Story 5.4.1's existing per-attempt line already has the hook) the raw `op` exit code + a hash/prefix of unmatched `stderr` whenever none of the fixed patterns match, so a drifted pattern is detectable from the log rather than silently swallowed forever. Optionally record the `op --version` the plan was validated against in the plan/ADR so a future regression has a known-good baseline to diff against. | P2 |
| 4 | Phase 2's structural redaction runs on **every** `AxSnapshot`-producing call (click/type/hover/select/press_key/snapshot), not just `type_secret` — the plan's own Risk Control section claims this is "a strict safety improvement... not a behavior change any caller should be relying on," but that's only true if the per-node CDP probe (`probe_redaction`) never misfires. A transient CDP error, a node briefly detached during eval, or an iframe/cross-origin restriction is fail-safe-redacted per design (`pitfalls.md` §3c) — correct for security, but it means ordinary non-secret fields (an email box, a search field) can start rendering `"[REDACTED]"` under exactly the kind of everyday flakiness (page still rendering, node churn) this daemon already handles for click/type actionability elsewhere. | Existing, previously-working (non-credential) browser-automation call sites start intermittently getting `"[REDACTED]"` back for ordinary text fields shortly after this ships — a functional regression in tools nobody asked to change, misdiagnosed at first as a probe bug rather than "working as designed" fail-safe behavior. | Add an explicit acceptance test (beyond Story 2.2.1c's happy-path unit tests) that forces `probe_redaction`/`collectRedactionInfo` into its failure path against a known-benign field and asserts the resulting redaction rate is bounded/logged — and add one line to the Observability Plan: log (once, rate-limited) when the fail-safe path fires for a node that isn't part of a `type_secret` call, so an operator can distinguish "probe is flaky" from "a real password field." | P2 |
| 5 | `op`'s own on-disk state (config/telemetry/session cache under the daemon's `$HOME`, distinct from the daemon's in-memory `id_cache`) is never audited by this plan. ADR-003 and the Risk Control section's "no persistent state to unwind... daemon holds no credentials at rest" claim is scoped to the daemon's *own* memory/state, not to what the external `op` binary itself may write to disk when invoked repeatedly with a service-account token. | A disk/backup/forensic review (or simply `find ~/.config/op` / `~/.op` after the feature has been in use) turns up cached item metadata or session artifacts the "no persistent state" claim didn't account for, undermining the regulated/confidential NFR classification's blanket claim. | Add a one-time verification task (like Task 4.1.1's spike) that runs `op` under the actual service-account invocation pattern this adapter uses and inspects the filesystem before/after for any new files, documenting the finding (even if "confirmed: none") in the plan the same way Unresolved Questions already tracks other UNVERIFIED items. | P3 |

## P1 Items (address before implementation)
- [x] Failure #1 — Added a "Known Residual Risk" subsection to `requirements.md` and a matching note in `plan.md`'s Risk Control section stating that redaction covers the MCP transport only, not the live page's own DOM/script access to a just-typed value. (2026-09-08)
