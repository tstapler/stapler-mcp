## Resolved Blockers (verified 2026-09-08)

- [x] **Task 1.1.1b / Task 3.2.2a — `CredentialRef.field` was a raw `String` at the port layer.** Fixed: `crates/core/src/ports.rs` now defines a closed `CredentialField { Username, Password, Totp }` enum with `#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash)]` and no `serde`/`schemars` derives (Task 1.1.1b, plan.md:256-266), used as `CredentialRef.field`'s type (plan.md:268-272). A separate wire-level `CredentialFieldInput` enum lives in `schema.rs` (Task 5.1.1a, plan.md:1577-1593). Task 3.2.1b/3.2.2a's `op` argv construction and the TOTP branch match exhaustively on `CredentialField` (`match credential_ref.field { CredentialField::Totp => ..., CredentialField::Username | CredentialField::Password => ... }`, plan.md:894-895) — no strings, no wildcard/fallback arm. Task 5.2.1b's tool-boundary conversion is a genuine exhaustive 1:1 match with no default case (plan.md:1690-1694: `CredentialFieldInput::Username => CredentialField::Username`, etc.), explicitly modeled on the cited `BrowserHistoryAction → HistoryAction` precedent (`crates/core/src/tools/browser.rs:764-766`). Task 4.3.1a converts `CredentialField` to a lowercase wire string via "the same small exhaustive match Task 3.2.1b/3.2.2a use" immediately before the `wasm_bindgen` extern boundary (plan.md:1449-1453), since JS has no enum type — this is the correct place for a string to reappear (crossing into JS), not a port-layer regression. No raw-`String`-typed `field` remains anywhere in `crates/core`'s port layer as planned.

- [x] **Phase 3 / Phase 4 (Epics 3.2 and 4.2) — ADR-003's in-flight-dedup mitigation had no implementing task.** Fixed: Story 3.2.5 (native, plan.md:983-1050) adds a `pending: RefCell<HashMap<CredentialRef, futures::future::Shared<...>>>` map to `NativeCredentialStore` (`crates/native/src/vault.rs`); `resolve()` checks the map first and joins the existing `Shared` future instead of spawning a new `op` call, removing the entry once the shared future completes (success or error) — genuine request coalescing, not a value cache, with concrete Given-When-Then ACs asserting exactly 1 `op` invocation for 2 concurrent identical `CredentialRef`s, exactly 2 for distinct refs, and an empty map once all waiters are served. Story 4.2.2 (wasm, plan.md:1361-1397) mirrors this with a module-level `pending` `Map<string, Promise>` in `vault.js`, keyed by `` `${domain}::${field}` ``, cleared via `.finally(() => pending.delete(key))` — same three ACs, same coalescing semantics (concurrent callers share the literal in-flight `Promise`, i.e. the same underlying SDK call). Both stories sit inside the same adapter-owned module (`NativeCredentialStore`/`vault.js`) that Blocker 3's DI fix (Story 3.4.0/4.3.0, injecting a single `Rc<dyn CredentialStore>` constructed once at daemon startup — Task 6.1.1a/6.1.2a) routes every `type_secret`-triggered resolve through, and Story 5.2.1's tool-layer function calls `browser.type_secret` exactly once and never calls `CredentialStore::resolve` directly (plan.md:1634-1641) — so the dedup map genuinely intercepts every resolve call rather than being bypassed. ADR-001's Consequences section now states this explicitly and cross-references Task 1.3.1a and Story 3.4.0/4.3.0.

## Concerns

- [ ] **Task 2.2.1a/2.2.1b — native redaction probing has no batching strategy and is asymmetric with the wasm side.** `probe_redaction` issues one `Runtime.callFunctionOn` CDP round trip per form-control-like node, and runs on *every* `capture_snapshot` call — i.e. after every click/type/hover/select/press_key, not just `type_secret`. The wasm equivalent (Task 2.3.1a) collects `{ref, type, autocomplete}` for every `input`/`textarea` in **one** `page.evaluate()` call. This is a real, unaddressed latency asymmetry between adapters that scales with form-field count on native but not wasm, and nothing in the plan's Observability/Risk Control sections disposes of it.
  **Recommendation**: Batch native's probe into a single page-wide `Runtime.evaluate` (or one `callFunctionOn` against the document, mirroring `collectRedactionInfo`'s shape) rather than N sequential per-node round trips.

- [ ] **Task 2.2.1b leaves open whether `walk_children` stays pure or takes `&Page`, risking a testability regression.** `build_tree`/`walk_children` in `crates/native/src/ax.rs` are today fully synchronous and `Page`-free — confirmed by reading the file: `walk_children`'s signature takes no `Page` argument, and its entire test module (`ax.rs:386-630`) constructs `RawAxNode` fixtures and calls `build_tree` directly with no live browser, which Task 2.2.1c calls out by name ("this file's existing 'no live `Page` needed' testing convention"). Task 2.2.1b's own text hedges: "`walk_children` itself, taking a `&Page` (check which keeps the pure-tree-walk unit tests working; if `walk_children` must stay `Page`-free for testability, add a resolution pass...)". Leaving this undecided at planning time risks an implementer threading async I/O through the recursive tree walk, breaking its current purity and unit-testability.
  **Recommendation**: Settle this now — mandate the "resolution pass over `refs` immediately after `walk_children` returns" approach (already named as the fallback), preserving `build_tree`/`walk_children`'s existing pure/synchronous/unit-testable shape.

- [ ] **Story 3.4.1/Task 3.4.1a — extending the shared `Action` enum with `TypeSecret(SecretValue)` couples vault-specific security policy into the general-purpose `dispatch_action` function.** `dispatch_action` (`crates/native/src/browser.rs:2463`) is the single shared body for Click/Type/Hover/SelectOption/PressKey/HistoryBack/HistoryForward/Reload — seven symmetric, low-complexity variants. Adding `TypeSecret` means this function must also host two behaviors unique to that one variant: a dispatch-time type/autocomplete refusal check (Task 3.4.1b, positioned between `verify_node_live` and dispatch) and unconditional own-node force-redaction after capture (Task 3.4.2a). This is an SRP/Open-Closed tension: the shared function's complexity is no longer uniform across its match arms, and a `SecretValue` now flows through the same enum/match that governs button clicks. (`Action` currently has no `Debug`/`Clone` derive, so this is not an active leak — but the coupling makes a future refactor that adds one riskier than it needs to be.)
  **Recommendation**: Implement `type_secret` as a thin wrapper that reuses `dispatch_action`'s factored-out primitives (session lookup, `resolve_locator_impl`, `verify_node_live`, `wait_and_capture`) directly, layering the refusal check and forced redaction on top in its own function — a Template Method shape — rather than extending the shared `Action` enum/match itself.

- [ ] **Story 2.3.1 — the plan's "same wire shape on both adapters" success metric does not actually hold, and Phase 2 doesn't close the gap.** Verified directly: `parseAriaSnapshot` (`crates/wasm/src/glue/browser.js:401-433`) never sets a `value` field on any node, and `JsAxNode.value: Option<String>` (`crates/wasm/src/browser.rs:114`, `#[serde(default)]`) therefore always deserializes to `None`. Wasm's `AxNode.value` is `None` for *every* field today, not just password fields — a pre-existing parity gap with native (which does populate `value` for textbox-like nodes) that predates this project. Story 2.3.1's redaction merge only substitutes `"[REDACTED]"` for matched nodes; it does not add general value population for the non-secret case, so after this plan ships, a legitimate (non-secret) textbox will show its typed value on native and never on wasm — the "same wire shape" claim in `requirements.md`'s Success Metrics is not achieved by the tasks as scoped.
  **Recommendation**: Either explicitly scope this pre-existing gap as out-of-scope with a one-line acknowledgment in the plan (so a reviewer isn't misled that Phase 7's parity acceptance test — Story 7.1.4 — actually proves full wire-shape parity, when it only proves `PortError` discriminant parity), or add the missing wasm value-population task.

- [ ] **Task 3.2.2a (downstream of the field-typing blocker) — no specified fallback for an unrecognized `credential_ref.field` value.** If `CredentialRef.field` stays a raw `String` (per the first blocker), `NativeCredentialStore::resolve`'s field branch has no named error/fallback arm for a value that is none of `"username"`/`"password"`/`"totp"`. This is resolved by construction if the first blocker's remediation (a real `CredentialField` enum) is adopted; flagging separately in case that remediation isn't taken as scoped.

## Nitpicks

- `CredentialRef`/`SecretValue` (Tasks 1.1.1b/1.1.1c) use public fields with no smart constructor guarding an empty `domain`, matching the existing (also-weak) `SessionId`/`Locator` tuple-struct convention. Given this feature's confidential/regulated NFR classification, a `debug_assert!(!domain.is_empty())` or equivalent would be cheap insurance, though it's consistent with existing repo style and low severity.
- Task 3.4.1b explicitly accepts spending a real vault round-trip before discovering a target field is the wrong shape ("cheaper than reordering and reopening the TOCTOU gap") — a reasonable, explicitly-justified tradeoff, but for the TOTP case it eats into the already-tight ~30s validity window `requirements.md`'s Rabbit Holes section flags. Worth a one-line acknowledgment in the plan's Risk Control section.
- The dispatch-time type-mismatch refusal (Task 3.4.1b) reuses `PortError::NotActionable` rather than a 6th vault-specific variant — reasonable per the plan's own stated reasoning, but means this refusal case falls outside the 5 named `Credential*` variants the Observability Plan's audit-log convention documents. A one-line cross-reference in `ux.md`/the Observability Plan would keep a future reader from assuming the 5 variants are the complete list of vault-related rejections.
