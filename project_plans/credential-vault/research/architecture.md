# Architecture Research: credential-vault

Agent 3 (Architecture). Design-only pass, no implementation. All line references verified against the working tree at commit `628ec11` (branch `tstapler/triage-6deab979-1c43-4daf-a5c5-909c6d8e53fe` off `main`) in `/home/tstapler/Programming/stapler-mcp`.

## 0. The crux, verified first

Requirement 3 asks whether a browser tool response ever echoes back what was typed. It does, unconditionally, today:

- `BrowserDriver::type_text` (`crates/core/src/ports.rs:281-287`) returns a full `AxSnapshot`, not just an ack.
- `AxNode.value` (`crates/core/src/ports.rs:151-162`) is documented as `Some(current_text)` for textbox-like nodes, "populated from the CDP AX node's own `value` property... lets a caller confirm typed text landed from `type_text`'s own returned snapshot."
- `browser_type` (`crates/core/src/tools/browser.rs:155-185`) passes that snapshot straight through `to_snapshot_output` into `BrowserActionOutput`, which is the JSON-RPC result the LLM/thin-client reads.
- `browser_fill_form` (`crates/core/src/tools/browser.rs:555-`) does the same for every field, including `BrowserFormFieldType::Textbox`.
- `browser_snapshot` (`crates/core/src/tools/browser.rs:195-221`) does a *fresh* AX capture and hits the identical code path — so even a tool call that never touched the field will re-expose it.
- Native adapter: `ax_value_to_string` (`crates/native/src/ax.rs:214-220`) passes the CDP `AXValue.value` straight through as a string — no masking for `input[type=password]`. Chromium's Accessibility domain reports the real value for password fields (masking is a visual/rendering concern, not an AX-tree concern), so this isn't a native-adapter bug to fix in isolation — CDP genuinely hands back the plaintext.

**Conclusion: any design that resolves the secret server-side but still returns an `AxSnapshot` (from the type call itself, or from any later `stapler_browser_snapshot`) leaks the plaintext into the LLM's context regardless of how the value got into the field.** Keeping the secret out of the *request* solves only half the problem addressed in the Problem Statement (the tool-call transcript exposing it on the way in); the response/snapshot path is a second, independent leak that has to be closed by redaction, not by request-side routing. This shapes every recommendation below.

## 1. Where secret resolution happens

### Wire-protocol reality check

The thin client is a dumb, stateless proxy — confirmed at `crates/cli/src/thin_client.rs:32-63`. `call_daemon` does `serde_json::to_value(input)` on the tool's typed input struct and forwards those exact bytes as `params` over the Unix socket (`client::call`); the daemon deserializes, runs the tool fn, and serializes the typed output straight back. There is no separate channel — **the Unix socket carries the identical JSON payload that constitutes the MCP request/response**. So "hand the daemon a value without going through a logged JSON-RPC field" is not achievable by routing through the socket differently; the socket *is* the JSON-RPC field, one hop later. The only way to keep a value out of that payload is to never put it in any tool's `In`/`Out` struct in the first place — i.e., don't send the plaintext over MCP *or* the socket. It has to be resolved on whichever side actually issues the CDP/Playwright call, using a reference, not a value, as the wire payload.

### Option (a): daemon resolves

The daemon already owns every piece of heavyweight, long-lived state — browser pool, HTTP clients, caches (per Problem Statement/Architecture context), and per the wasm glue (`crates/wasm/src/glue/browser.js:1-31`) it owns the single long-lived Playwright/Chrome process for the whole daemon lifetime, lazily started once. `page.type()` calls only ever happen inside the daemon process (native: `chromiumoxide` calls in `crates/native/src/browser.rs`; wasm: `playwright-core` calls in the Node glue). A daemon-side vault lookup therefore composes directly with a call the daemon is already making — no new process boundary, no new IPC hop between "have the secret" and "type the secret." This is the same shape as every existing port: the daemon is the only process with OS/network access (`crates/core` is `#![no OS calls]`; only `crates/native`/`crates/wasm` adapters, which the daemon links, touch the OS).

### Option (b): thin-client resolves

The thin client is spawned fresh per Claude Code session (`crates/cli/src/thin_client.rs:1-3`, "The stdio MCP server Claude Code actually launches... auto-starting [the daemon] on first use") and holds no state between calls. Giving it vault access means either (1) re-authenticating to the vault (e.g., `op` CLI session) on every session start — worse UX and a wider blast radius (every Claude Code session process gets vault credentials, not just the one daemon), or (2) the thin client still has to hand the daemon *something* to act on, and per the wire-protocol reality above, whatever it hands over the socket is exactly as visible as an MCP field, so this option doesn't actually avoid a socket-visible payload — it just moves who resolves it. It would also require the thin client to reach across the socket into live CDP/Playwright objects it doesn't own, which doesn't exist as a capability today and cuts against every other port's design (the daemon is the sole OS-touching process by construction).

### Recommendation

**Daemon resolves (option a).** It's the option consistent with "daemon owns heavyweight state," it doesn't require inventing a new capability (thin client reaching into live browser objects), and it doesn't actually buy privacy that option (b) lacks, since the socket-vs-MCP distinction the requirements draw doesn't hold — same bytes, one hop later.

### Where the vault-access secret itself lives

Either way, *something* needs standing access to 1Password. With daemon-side resolution that's a 1Password **service account token** (scoped, non-interactive, revocable — not the user's personal `op` session) living in the daemon process's environment, read once at daemon startup via the existing `EnvPort` (`crates/core/src/ports.rs:105-109`) — same pattern as any other daemon-only secret. It should NOT live in `~/.stapler-mcp/` config read by the thin client (that file's readable-by-thin-client-process boundary is exactly the one this design keeps the plaintext credential out of) — it belongs in the daemon's own launch environment (e.g. set in the systemd/launchd unit or shell profile that starts `stapler-mcp-daemon`, or read from the OS keychain via the native adapter's future `keyring` integration — see §4). The daemon is already the single-user, local-only, unauthenticated trust boundary (per `stapler_browser_close_all_sessions`'s documented rationale) — it is already the place that's trusted with everything on this machine; adding a vault-access token to that trust boundary doesn't create a new exposure, it reuses the existing one.

## 2. Extending `BrowserDriver`

**Reuse `type_text` with a flag is wrong.** A boolean/enum flag on the existing method still forces the caller to pass a plaintext `text: &str` argument for the non-secret case and doesn't change the *return type*, which is the actual leak (§0). Flags on a method whose signature takes the raw value invite exactly the mistake of typing the secret through the flagged path anyway.

**Add a distinct method that never accepts or returns plaintext:**

```rust
/// Opaque, non-secret domain/key identifier the daemon resolves against its
/// own vault access — never carries a credential value. Distinct from
/// `Locator`, which identifies a DOM node; `CredentialRef` identifies a
/// vault entry.
pub struct CredentialRef {
    pub domain: String,   // e.g. "example.com" — used for domain-scoped lookup policy
    pub field: String,    // e.g. "password", "username", "totp"
}

async fn type_secret(
    &self,
    session_id: &SessionId,
    locator: &Locator,
    credential_ref: &CredentialRef,
    timeout: Duration,
) -> Result<AxSnapshot, PortError>;
```

But per §0, returning a plain `AxSnapshot` here just re-leaks the value through `AxNode.value`. So `type_secret`'s contract must additionally redact: the returned snapshot's `value` field for the node just filled (and — see §3 — for any node the daemon can identify as a password-type control) must never be the literal secret. Two implementation options for the port boundary itself (both design-compatible, pick during planning):

1. `type_secret` returns `AxSnapshot` but the *adapter* (native/wasm) is contractually required to substitute a fixed placeholder (e.g. `Some("••••••••")`) for the acted-on node's `value` before returning — same shape as `type_text`, different content guarantee.
2. `type_secret` returns a narrower `Result<(), PortError>` (no snapshot at all), forcing the caller to make a separate `snapshot()` call if it wants to see the resulting form state — which then hits the redaction rule in §3 uniformly.

Recommend (1): keeps parity with every other mutating call's "get a fresh snapshot back" ergonomics (matches `click`/`type_text`) while making the redaction guarantee part of the method's contract, documented the same way `navigated_from` is documented today.

## 3. Snapshot redaction has to be structural, not call-scoped

Because `browser_snapshot` (§0) independently re-derives an `AxSnapshot` from live CDP/Playwright state with no memory of which tool call filled which field, redacting only inside `type_secret`'s own response is insufficient — the very next `stapler_browser_snapshot` call re-exposes the value from the DOM directly. Redaction has to live where **every** `AxSnapshot` gets built, keyed off something durable: the underlying control's `type` attribute (`input[type=password]`), not call history. Concretely, in `crates/native/src/ax.rs`'s `build_tree`/`ax_value_to_string` path (`ports.rs:214-220`), before setting `AxNode.value`, the adapter needs one more piece of information CDP's `Accessibility.getFullAXTree` doesn't hand over for free today: the DOM node's `type` attribute. That's fetchable via `DOM.describeNode` (already imported at `crates/native/src/ax.rs:20`, currently used for a different purpose) or a small JS eval against the resolved node (the codebase already has this pattern — `crates/native/src/browser.rs:802`'s `function(text) { this.focus(); this.value = text; ...}` for `type_text` shows eval-on-node is a well-worn path). Whichever field type comes back as `password`, always substitute a fixed-length placeholder for `value`, independent of which tool call is asking. This also incidentally fixes a **pre-existing, out-of-scope-today leak**: a page with a browser-autofilled password field, snapshotted with the *current* code, already exposes that value with zero credential-vault involvement — worth flagging to the requirements owner as a related but separable bug, not something this design needs to fix, but something a reviewer should not be surprised already exists.

The wasm adapter needs the equivalent: Playwright exposes `elementHandle.evaluate(el => el.type)` or an accessibility snapshot with `role`/attributes; the redaction rule must be applied in `crates/wasm/src/glue/browser.js`'s snapshot-building function symmetrically, since both adapters implement the same `BrowserDriver` contract and a design that's safe on native but leaky on wasm (or vice versa) fails the "identical wire protocol" requirement.

## 4. A new `Vault`/`CredentialStore` port

Yes — this is the right shape, consistent with the existing 8-port pattern (`SocketFactory`, `ProcessLock`, `ProcessSpawner`, `EnvPort`, `ClockPort`, `HttpClient`, `FileStore`, and `BrowserDriver` itself, all in `crates/core/src/ports.rs`). `crates/core` stays `#![no OS calls]`; the port is a trait, adapters do the OS/process/network work:

```rust
pub trait CredentialStore {
    /// Resolves `credential_ref` to a secret value. Never logged, never
    /// included in any Debug/Display impl (see rust-idioms guidance on
    /// wire/domain type separation — this type should NOT derive Debug,
    /// or should hand-roll a redacting one).
    async fn resolve(&self, credential_ref: &CredentialRef) -> Result<SecretValue, PortError>;
}
```

- **Native adapter** (`crates/native/src/`, new `vault.rs`): shell out to `op read` / `op item get` via the existing `ProcessSpawner` port (reuse, don't duplicate, the process-spawn plumbing `crates/native/src/spawn.rs` already has) or use the `keyring` crate for OS-keychain-backed local caching of short-TTL resolved values. Shelling out to `op` is the lower-effort, more auditable option (1Password's own CLI does the TOTP/2FA/session handling); `keyring` is a reasonable *cache* layer in front of it, not a replacement for it, since it doesn't know how to talk to 1Password's vault itself.
- **Wasm adapter** (`crates/wasm/src/glue/`, new `vault.js`): call 1Password's Node SDK (`@1password/sdk`) via the same wasm-bindgen import-object glue pattern already used in `crates/wasm/src/glue/browser.js` (module-level lazy singleton, e.g. `getVaultClient()` mirroring `getBrowser()` at `browser.js:7-12`) — one shared authenticated client for the daemon's lifetime, not re-authenticated per call.

`SecretValue` should be a newtype wrapper (`SecretValue(String)`) with a hand-rolled `Debug` that never prints the inner value, so an accidental `{:?}` in a log statement or error message can't leak it — this is the same category of discipline the codebase already applies to `PortError`'s message construction (`crates/core/src/tools/browser.rs:77-90`'s comment about not double-wrapping driver messages shows the team already treats error-message construction as something to get precisely right).

## 6. TOTP/2FA flow (added for Large-appetite scope)

### How 1Password actually generates the code

- **CLI (native adapter)**: `op item get <item> --otp` prints the item's current TOTP code and is documented to work with service-account tokens ([1Password CLI `item` reference](https://www.1password.dev/cli/reference/management-commands/item); confirmed workable with `OP_SERVICE_ACCOUNT_TOKEN` in community reports — [Retrieve password and OTP in a single CLI command](https://www.1password.community/developers-69/retrieve-password-and-otp-in-a-single-cli-command-1134)). One documented constraint: **service-account invocations must pass `--vault` explicitly** — unlike an interactive `op` session, a service account has no default-vault inference to fall back on. This is a real, must-not-skip argument for the native adapter's `op item get`/`op read` calls, not an optional nicety.
- **Node SDK (wasm adapter)**: `@1password/sdk`'s `items.get()` method does **not** return OTP values — it's documented as unsupported/returns empty for that field ([`onepassword-sdk-python` issue #59](https://github.com/1Password/onepassword-sdk-python/issues/59), same SDK family/limitation as the JS SDK). The correct call is `client.secrets.resolve()` against a secret reference with an explicit `?attribute=otp` query parameter (`op://vault/item/field?attribute=otp`), not the item-get path. **This means the wasm `CredentialStore` adapter needs a field-conditional branch** (`field == "totp"` → `secrets.resolve(ref + "?attribute=otp")`; everything else → the item-field path) — a single uniform "read this field" code path across both credential kinds, which §4's original sketch implicitly assumed, does not actually work for the wasm side. The native `op item get --otp` path doesn't have this split (one flag covers it), so this is also a **native/wasm asymmetry** worth flagging against the requirements' own "identical wire protocol... same guarantee" success metric (`requirements.md` Success Metrics, 4th bullet) — the *guarantee* stays identical, but the *adapter-internal mechanism* to reach it necessarily differs per backend, which should be documented rather than assumed away.

### Timing: is the ~30s window actually at risk?

Traced the concrete latency path rather than estimating it:

- Native `dispatch_type`'s actionability gate (`crates/native/src/browser.rs:792-808`, `retry_until_actionable` at line 759) retries on the fixed Playwright-mirrored backoff `[0, 20, 100, 100, 500]` ms (comment at `browser.rs:647-648`) — worst case ~720ms of waiting *before* the DOM write is attempted, only in the case where the field isn't immediately actionable (covered by an overlay, mid-animation, etc.). This is bounded and small relative to a 30s window.
- The dispatched write itself is **atomic, not per-keystroke**: native's `dispatch_type` sets `this.value = text` in a single JS eval (`browser.rs:802`, unchanged since the original research's citation), and the wasm adapter uses Playwright's `locator.fill(text, ...)` (`crates/wasm/src/glue/browser.js:583`) — also a single atomic set, not `pressSequentially`/`.type()`'s character-by-character simulation. Neither adapter can leave a field holding a truncated prefix of the secret from a mid-dispatch failure; the write either lands whole or the field is untouched (see §9).
- The genuinely variable cost is the **vault round-trip itself**: a service account (mandated by requirements — not the user's interactive `op` session) has no local desktop-app integration to short-circuit through, so every `op item get --otp`/`secrets.resolve(...&attribute=otp)` call is a real network round-trip to 1Password's service, not a local IPC call. Under normal connectivity this is comfortably sub-second and well inside a 30s TOTP step; it becomes a real risk only under degraded network conditions, or if a caller resolves the TOTP once and then sits on it before calling `type_secret` (e.g., an LLM that resolves the code, then does several unrelated tool calls before typing it) — **the design should make `resolve` and `type_secret` a single tight daemon-side operation for the TOTP field specifically** (resolve immediately before dispatch, not resolved earlier and threaded through as a value — which the existing `CredentialRef`-not-`SecretValue`-over-the-wire design already guarantees, since the *caller* never holds the resolved value to begin with; the risk is confined to how long `type_secret`'s own implementation holds the value in daemon memory between `CredentialStore::resolve` and the DOM write, which should be "as short as possible, no intermediate caching layer" for `field: "totp"` specifically, even though a cache is explicitly fine for `field: "password"`/`"username"` per the NFR section's "resolved-value cache... valid future optimization").

### The redaction gap TOTP introduces

**This is the most consequential finding of this pass.** §3's structural redaction rule, and requirements.md's own Scope description (line 98: "substitute a fixed placeholder for any node whose underlying DOM `type` attribute is `password`"), key redaction *exclusively* off `input[type="password"]`. Real-world OTP/2FA input fields are, by current web-platform convention, generally **not** `type="password"` — the documented best practice is `<input type="text" inputmode="numeric" autocomplete="one-time-code" pattern="\d{6}">`, and using `type="password"` for an OTP field is explicitly discouraged because `autocomplete="one-time-code"` doesn't suppress the browser's own password-save prompt when paired with `type="password"` ([Twilio: Best Practices for OTP Input Forms in HTML](https://www.twilio.com/en-us/blog/developers/best-practices/otp-input-forms-html); consistent with [web.dev's SMS OTP form guidance](https://web.dev/articles/sms-otp-form)). Concretely: **a TOTP code typed via `type_secret` into a real-world OTP field, then exposed through the very next `stapler_browser_snapshot`, would sail straight through the `type=password`-only structural filter and leak in full** — the exact class of leak this whole feature exists to close, reopened for the one credential type (TOTP) that's new in this pass.

Two independent fixes are needed, and both are cheap given work already scoped:

1. **`type_secret`'s own acted-on-node substitution (§2 option 1) must be unconditional**, not gated on re-detecting the DOM `type` attribute at all — the daemon already knows the node it just wrote a secret into, from its own `locator` argument, regardless of what `type`/`autocomplete` the DOM reports. This was implicit in the original design but should be made an explicit invariant: "the node named in `type_secret`'s own `locator` is always redacted in that call's returned snapshot, independent of field-type detection."
2. **The structural sweep (§3, for *every* `AxSnapshot`, not just the one `type_secret` itself returns) needs a wider key.** `DOM.describeNode` (native) / `elementHandle.evaluate(el => ...)` (wasm) already fetch the node's full attribute set in one call — reading `autocomplete` alongside `type` costs nothing extra mechanically. Recommend redacting when **`type == "password"` OR `autocomplete` is one of `one-time-code`, `current-password`, `new-password`** (the last two are the WHATWG autofill-detail tokens password managers themselves key off; including them is a small amount of extra defense-in-depth against non-`type=password` password fields, which exist too, for the same "developer skipped the platform convention" reason OTP fields do). This is a widened *key*, not a redesign — it fits inside the same "structural, not call-scoped" mechanism §3 already specified.

### Partial failure mid-2FA-flow

Per requirements' `CredentialRef{domain, field}` shape and `type_secret`'s single-locator, single-field signature, **a "login + TOTP" flow is inherently two separate `type_secret` calls driven by the caller** (password field, then — after the caller snapshots and spots an OTP-shaped field — a second call with `field: "totp"`), not one daemon-side atomic transaction. See §9 for the full failure-mode analysis; the short version, grounded in the atomic-dispatch finding above: neither call can leave a field holding a truncated/partial secret, but a TOTP field's redaction coverage in the *failed* state depends entirely on the widened key from the previous subsection — without it, a TOTP value that lands in the DOM but whose `type_secret` call reports failure (e.g., a CDP response lost after the eval already executed server-side) is invisible to the daemon's own error handling but fully exposed to the next snapshot.

## 7. Domain-matching and disambiguation rule

### Existing precedent in this codebase

This is not a green-field decision — `stapler-mcp` already has a security-critical "does this URL belong to domain X" check for the SSRF guard, added the same week as this research (`3f3ddc8`, `feat: configurable SSRF allowlist and auditable deny log (#41)`), and it sets a clear, load-bearing precedent:

- `same_host` (`crates/core/src/tools/webcrawl.rs:125-126`): `a.host_str().is_some() && a.host_str() == b.host_str()` — **exact host-string equality**, no suffix/eTLD+1 logic at all, used to decide whether the crawler stays within a domain.
- `blocked_host_reason`'s allowlist check (`webcrawl.rs:247-259`): also exact match against a `HashSet<String>` of lowercased hostnames, with an explicit comment (`webcrawl.rs:248-250`) about a real bug this exact-match approach already tripped over once — `Url::host_str()` brackets IPv6 literals (`"[fe80::1]"`), which silently never matched a plain-written allowlist entry until fixed by re-deriving the comparison key from `Host`'s `Display` impl instead.
- The one place this codebase does suffix matching (`.localhost`, `webcrawl.rs:234`) does it correctly, with an explicit leading-dot boundary (`d.to_ascii_lowercase().ends_with(".localhost")`) — guarding against exactly the bug class where `"evil-localhost".ends_with("localhost")` would wrongly be `true` without the dot.

**Recommendation: domain-matching for `CredentialRef.domain` should be exact host-string equality, mirroring `same_host`/`EnforceWithAllowlist` — not suffix, not eTLD+1, not substring.** This is consistent with the existing codebase convention (so it's one policy shape for reviewers to reason about, not two), requires no new dependency (a public-suffix-list crate is real complexity for correctly computing eTLD+1 — e.g. `co.uk`, `github.io` — that this design doesn't need if exact match is the rule), and is the strictest option, which matches this feature's "confidential/regulated" NFR classification (`requirements.md` Non-functional Requirements). The cost is real but bounded: a login page hosted on `accounts.example.com` while the vault item's URL is recorded as `example.com` requires the vault item's URL field (or the `CredentialRef.domain` the caller passes) to literally say `accounts.example.com` — no automatic subdomain generosity. That's a usability tax, not a correctness bug, and it's the safer failure direction (reject-and-retry-with-the-right-domain beats silently widening the match).

### Where "current domain" comes from, and why that's the actual risk surface

The matching *algorithm* being exact-string is necessary but not sufficient — the more consequential design question is **what URL gets compared**, because that's where a spoofing attack would actually have to land. The comparison must be against the daemon's own live navigation state for the session (the same source `AxSnapshot.url` and the SSRF preflight already trust — CDP/Playwright's own reported page URL), read fresh at `type_secret` dispatch time, never a value supplied by the caller or read from anything the page's own JS/DOM content could influence (page `<title>`, a spoofed on-page "you are logged into example.com" banner, `document.URL` overridden by injected script, etc.). Given the exact-match rule above, **an attacker needs literal DNS/TLS control of the exact domain string to pass the check** — genuinely equivalent to a real domain compromise, not a phishing page merely resembling or embedding the target's name. This directly answers the task's blast-radius question: **the matching rule itself is not the exploitable surface if implemented as "exact match against the daemon's own freshly-queried navigation URL"; the exploitable surface would be a staleness bug** — checking a URL captured from an earlier snapshot/tool call instead of one queried at the moment of dispatch. That's not hypothetical for this codebase: `6b6b56a`/`6a0f576` ("race SSRF redirect detection against goto") is exactly this bug class, already found and fixed once for the SSRF guard on this same branch. The domain check for `type_secret` needs the identical treatment — evaluated against a URL queried in the same call as (or immediately before) the actionability check and dispatch, not cached — and ideally through one shared helper the SSRF guard and the credential-domain guard both call, rather than two adapters independently reimplementing "is this the domain I think it is," which is exactly the kind of duplication that let the SSRF version of this bug exist in the first place.

### Disambiguation: `CredentialRef`'s shape doesn't actually support it

`CredentialRef { domain, field }` (`requirements.md` Scope, confirmed as the whole struct — no item selector) has no way for a caller to pick between two vault items that both match a domain exactly. This is framed in requirements.md as an edge case ("reject... when the lookup is ambiguous"), but it's a **common real-world case**, not a rare one: a user with a personal and a work account on the same domain, or multiple Login items someone saved for the same site over time, is unremarkable in a real 1Password vault. As specified, `type_secret` has no way to succeed for that domain at all — every call is rejected as ambiguous, permanently, regardless of caller intent. Recommend surfacing this in planning as a real gap, not just "reject": add an optional disambiguator to `CredentialRef` (e.g. `item: Option<String>`, matched against the 1Password item's title or ID) that's required only when the domain-scoped lookup is actually ambiguous — i.e., the single-item-per-domain case stays exactly as simple as designed, and the multi-item case gets a second round-trip (daemon rejects with the candidate item titles/ids in the error so the caller/LLM can retry with a disambiguator) rather than a permanent dead end. This also needs an answer for **how** ambiguity is even detected mechanically: neither `op item list`'s documented filtering flags nor the 1Password Node SDK were confirmed (in the research for this pass) to expose a native "list items matching this URL" query — UNVERIFIED, flagged as a planning-phase spike, not resolved here — so the adapter likely has to list Login-category items itself and filter by each item's `urls[].href` host client-side, which is exactly where the exact-match-vs-caller-supplied-domain comparison from the previous subsection needs to be applied consistently on the vault-item side too (an item whose saved URL is `www.example.com` and a page at `example.com` are, under the same strict rule, a mismatch — worth deciding explicitly rather than by accident of whichever string comparison gets written first).

## 8. Redacted placeholder shape

**Recommendation: a fixed, constant sentinel string, identical for every redacted field regardless of the real value's length or content — never derived from the secret in any way.** Concretely: a single global constant (e.g. `"[REDACTED]"`), not `"•" * len(secret)` or any other shape/length-preserving scheme.

Reasoning:

- **Length is itself sensitive information.** A masked-but-length-preserving placeholder (the classic browser-UI bullet-per-character convention) tells an observer — here, the calling LLM's context, and anything downstream of it — the exact character count of the real secret across every snapshot it appears in. For a password, that narrows the space of what it could be; for a resolved TOTP code, length is nearly fixed (6 digits) so it's low-signal there specifically, but the placeholder mechanism is shared across both `field` values by design (§3/§6), so the password case governs the choice. This reasoning is general security-engineering practice (password-masking-length as a side channel), not sourced from a specific citation for this codebase.
- **A non-mimicking sentinel avoids a category of caller confusion a bullet-string doesn't.** If the placeholder looks like ordinary masked-password UI text (`"••••••••"`), a caller (LLM) reasoning about the snapshot has no textual signal that this value is a *policy redaction* rather than what a human would see rendered in the browser — it could plausibly try to "verify" the value some other way, or treat the bullets as meaningful data. `"[REDACTED]"` (or similar, unambiguously non-password-shaped bracketed text) reads unambiguously as "this tool intentionally withheld this," matching the same self-describing-error-message convention this codebase already uses elsewhere (e.g. the `NotFound`/`NotActionable` error strings surfaced by `browser.rs`, which are written to be directly actionable rather than opaque).
- **Zero new information leaks even in the presence-vs-absence sense the placeholder controls.** The *fact* that a field was filled is already visible from the field's `role`/`name` and the AxSnapshot structure regardless of redaction (this was true before credential-vault too); the placeholder's job is narrowly to make sure the *value* carries nothing beyond that already-visible fact. A fixed sentinel does exactly that; a length-preserving one doesn't.

This also settles §6's redaction-widening cleanly: the same fixed sentinel applies whether the redaction trigger was `type=password` or the widened `autocomplete` check — one constant, two trigger conditions, no per-field-kind placeholder variants to keep in sync.

## 9. Compliance/security-critical failure modes

### Partial failure: password resolves, TOTP generation fails mid-flow

Restating the mechanical facts established in §6 precisely, because the answer depends on them: `type_secret` is called once per field, and each call's DOM write is atomic (`this.value = text` / Playwright `.fill()` — §6), not incremental. So:

- **The password field cannot be left "half-typed."** Either the first `type_secret(field: "password")` call's DOM write completes and the field holds the full, real password, or it fails before the write (actionability timeout, vault-lookup failure) and the field is untouched. There is no intermediate DOM state where a partial password string sits in the field.
- **If the *second* call (`field: "totp"`) fails — for any reason, including 1Password's own TOTP-generation step failing — the password field from the first call is unaffected and still holds the real, typed password value in the live DOM**, because the two calls are independent `type_secret` invocations against different locators; nothing about the second call's success or failure touches the first field. That password value's redaction coverage is fine: it's `type="password"` by definition of being a password field, which the existing (pre-TOTP) structural rule already covers.
- **The actual gap is the TOTP field's own state on failure, and it's exactly the one described in §6's redaction-gap subsection**: if 1Password's TOTP generation itself fails (network error, service-account permission issue, expired token), the daemon has nothing to write — `CredentialStore::resolve` returns `Err` before `type_secret` ever calls the browser driver, so the OTP field is never written to at all in that failure mode, and there's nothing to leak. The scenario that *does* need coverage is the narrower one flagged in §6: the DOM write itself apparently-fails (CDP response lost) after having actually executed server-side — a real value sitting in a field the daemon believes is empty/failed. Requirements' own Risk Control section says "no silent fallback to plaintext" for the *request* side; this finding is the *response*-side analogue of that same discipline, and it's covered structurally only once the `autocomplete`-widened redaction key from §6 ships — with only the original `type=password` key, this specific failure mode leaks the TOTP code in full on the next snapshot.
- **Actionable error surfacing** (required by requirements' Scope, "Actionable vault-error surfacing... no silent plaintext fallback") should distinguish this case in its error message: "resolved but failed to type" (the DOM-write-ambiguous case above) is a materially different, higher-severity situation than "vault lookup failed, nothing was ever typed" (`CredentialLookupFailed` in §5's original table), and a caller/operator needs to know which one happened — the former means "assume the value may be live in the DOM until confirmed otherwise," the latter means "nothing happened, safe to retry."

### Blast radius if the domain-matching rule has a bug

Answered in depth in §7; summarizing the specific "could it type the wrong site's credential into a phishing page that spoofs a known domain string" scenario asked here: **under the recommended exact-host-string-match rule, sourced from the daemon's own freshly-queried CDP/Playwright navigation URL (not caller input, not page content) — no.** A phishing page at `paypa1.com` or `example.com.attacker.net` or one that overlays fake branding never produces a `host_str()` that's exactly `"example.com"`; passing the check requires the literal string equality, which requires actual control of that domain's DNS. The blast radius of a *bug* in this design (as opposed to the design being theoretically sound but wrongly implemented) concentrates in exactly two places, both identified in §7: (1) a staleness bug — checking a URL captured before the most recent navigation/redirect rather than one queried at dispatch time (the precise bug class `6b6b56a` already fixed once, for SSRF, on this branch), and (2) an accidental loosening of "exact" into something suffix/substring-based during implementation (e.g. a well-intentioned `.ends_with(domain)` added later to "support subdomains" without the dot-boundary guard the codebase's own `.localhost` check demonstrates is required — `"evil-example.com".ends_with("example.com")` is `true`). Both are implementation-discipline risks, not design gaps, which is why §7 recommends a single shared domain-comparison helper reused by both the SSRF guard and the credential-domain guard, rather than two independent implementations that could drift apart under exactly this kind of "helpful" future edit.

## 10. Updated Event-Command-Policy table (revises §5)

The original §5 table's `TwoFactorChallengeDetected` row was written when TOTP was out of scope and explicitly hedged ("out of scope for this pass... but the table names the seam"). With TOTP now in scope and `type_secret`'s actual signature nailed down (single `locator` + single `credential_ref`, no page-state awareness), the answer to this pass's framing question is concrete: **`TwoFactorChallengeDetected` is not a real daemon-side event and should be removed as a "detection" row.** Nothing in this design gives the daemon a reason to look at a page unprompted — there's no listener, no poll loop, no "notice the page changed" mechanism anywhere in `BrowserDriver` or the daemon's architecture (confirmed: the daemon only acts inside a tool call the caller made). The daemon never "detects" a 2FA challenge; **the calling LLM does, by reading an ordinary `stapler_browser_snapshot`/`type_secret` response and recognizing an OTP-shaped field the same way it already has to recognize any other field** (`browser_fill_form`'s existing per-field-type dispatch is the precedent: the caller identifies fields from a snapshot today, with zero daemon-side "field understanding"). The 2FA flow is therefore not a new event/policy pair at all — it's the exact same `CredentialTypeRequested → ResolveCredential → ...` row, invoked a second time, with `credential_ref.field = "totp"` and a different `locator`. ## Summary of recommendations

1. Daemon resolves credentials (not the thin client) — consistent with "daemon owns heavyweight state," and the thin-client/daemon Unix-socket hop carries the same bytes as the MCP JSON-RPC payload, so routing through the socket differently buys no privacy the daemon-side approach lacks.
2. Add `BrowserDriver::type_secret(session_id, locator, credential_ref, timeout) -> Result<AxSnapshot, PortError>` taking an opaque `CredentialRef` (domain/field, no value) — not a flag on `type_text`.
3. **The crux, confirmed in code, not assumed**: `type_text`, `browser_fill_form`, and `browser_snapshot` all currently return the field's live value via `AxNode.value` (`crates/core/src/ports.rs:151-162`, wired through unredacted in `crates/native/src/ax.rs:214-220`). A `CredentialRef`-only request is necessary but not sufficient — snapshot redaction of `password`-type fields must be structural (applied wherever any `AxSnapshot` is built) or the secret leaks back to the LLM on the very next snapshot call regardless of how it got into the field.
4. Add a `CredentialStore` port alongside the existing 8 — native adapter shells out to `op` (optionally cached via `keyring`), wasm adapter uses 1Password's Node SDK through the existing wasm-bindgen glue pattern (`crates/wasm/src/glue/*.js`) — and give `SecretValue` a non-leaking `Debug` impl.
