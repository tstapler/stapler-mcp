# Research: Architecture for MCP-over-Streamable-HTTP in the daemon

**Input**: [`project_plans/mcp-streamable-http/requirements.md`](https://github.com/tstapler/stapler-mcp/blob/628ec11be71645f42ecbe6dcd11d432c52f4a4e6/project_plans/mcp-streamable-http/requirements.md)
**Commit cited throughout**: `628ec11` (current `HEAD`)

## New empirical finding not yet in requirements.md

**The `!Send`/wasm-shared-code constraint is still live and load-bearing — it is not dead code to relax for free.**

[`crates/wasm/src/lib.rs:17,52`](https://github.com/tstapler/stapler-mcp/blob/628ec11be71645f42ecbe6dcd11d432c52f4a4e6/crates/wasm/src/lib.rs#L17-L52) imports `stapler_mcp_core::daemon::{json_handler, Daemon}` and constructs `Daemon::new()` inside `#[wasm_bindgen] pub async fn run_daemon()`, registering the same 17 tools (all except the 5 docs/embedder tools, which are native-only per [`crates/core/src/ports.rs:409-415`](https://github.com/tstapler/stapler-mcp/blob/628ec11be71645f42ecbe6dcd11d432c52f4a4e6/crates/core/src/ports.rs#L409-L415)) via the identical `json_handler`/`daemon.register` pattern used in [`crates/cli/src/main.rs::run_daemon`](https://github.com/tstapler/stapler-mcp/blob/628ec11be71645f42ecbe6dcd11d432c52f4a4e6/crates/cli/src/main.rs#L60). This answers requirements.md's open question directly: `crates/wasm` has **not** diverged from `crates/core::daemon::Daemon` — it reuses the exact same `!Send` type. Making `crates/core::daemon::Daemon` (or its state) `Send`/`Arc<Mutex<...>>`-based to satisfy `rmcp`'s HTTP transport would force the same change onto the wasm adapter, which is explicitly out of scope per requirements.md's "Out of Scope" section. This rules out "just relax `!Send` in core, it's free" as an option.

## `rmcp` API confirms there is no escape hatch

Read directly from the vendored crate at `~/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/rmcp-2.2.0`:

- `rmcp`'s `Cargo.toml` (`[features]`, line 85) defines a `local` feature: `local = ["rmcp-macros?/local"]`. This feature relaxes the core `Service<R>` trait itself, from `pub trait Service<R: ServiceRole>: Send + Sync + 'static` (`src/service.rs:136`, default) to `pub trait Service<R: ServiceRole>: 'static` (`src/service.rs:151`, `#[cfg(feature = "local")]`) — i.e. `rmcp` already has infrastructure for `!Send` servers (this is presumably how `ThinClient` over stdio, or a wasm MCP server, could someday drop the bound).
- **But `StreamableHttpService`'s own `tower_service::Service` impl is not feature-gated.** There is exactly one `impl<RequestBody, S, M> tower_service::Service<...> for StreamableHttpService<S, M>` in `src/transport/streamable_http_server/tower.rs:571`, unconditionally bounded `S: crate::Service<RoleServer> + Send + 'static`. No `local`-feature variant of this impl exists. So even building `rmcp` with `local` enabled does not let a `!Send` `ThinClient`-equivalent plug into `StreamableHttpService`. This is the strongest possible confirmation of requirements.md's verified finding — it's not just one bound in one file, it's the *only* Send-relaxation path in the crate and it still doesn't cover the HTTP transport.
- **Session lifecycle**: `StreamableHttpService::new` takes a `service_factory: impl Fn() -> Result<S, io::Error> + Send + Sync + 'static` (`tower.rs:632`). Per the doc comment on `spawn_session_worker` (`tower.rs:651-656`, "Spawn a task that runs `serve_server` for the given session..."), the factory is invoked once per new HTTP/SSE session, and that session's `S` instance is driven inside its own `tokio::spawn`'d task. This is a concrete, load-bearing fact for the design: **each concurrent HTTP session gets its own fresh `S`, spawned as an independent `Send` task** — this is structurally identical to the stdio thin client's role (one `ThinClient` instance per connection), just multiplied per HTTP session instead of per OS process.

This last point is decisive: it means the natural shape of an `S` for the HTTP path is a small, cheap, `Send`-bound struct constructed per session — exactly analogous to today's `ThinClient` — not a redesign of the daemon's core state itself.

## Option A — `Arc<Mutex<...>>` rewrite, single `Send` runtime

**Invasiveness across `crates/native`**: high, and not a bounded-scope change. `crates/native/src/browser.rs` is 3466 lines and contains 65 separate `Rc<RefCell<...>>` construction/access sites (`grep -c` verified) for `NativeBrowser`'s session table (`sessions: Rc<RefCell<HashMap<String, BrowserSession>>>`, [`browser.rs:298`](https://github.com/tstapler/stapler-mcp/blob/628ec11be71645f42ecbe6dcd11d432c52f4a4e6/crates/native/src/browser.rs#L298)), per-session ref-resolution caches (`latest_refs`, `known_refs`, `blocked` at `browser.rs:127,132,154`), and more. None of these were written with lock-ordering discipline in mind — the whole point of the `Rc<RefCell<...>>` design (per `daemon.rs`'s doc comment) was to avoid ever needing to reason about concurrent mutation. Converting this to `Arc<tokio::sync::Mutex<...>>`/`Arc<RwLock<...>>` requires auditing every one of those 65+ sites for: (a) holding a lock across an `.await` (a bug class the current `!Send` design structurally can't have, since `RefCell` borrows are explicitly documented as "never held across an `.await`" in `daemon.rs:59-60`), and (b) reentrant/recursive lock acquisition inside the same call chain (e.g. does any browser-tool function call another browser-tool function that also locks `sessions`?) — not verified false without reading all 3466 lines, which is itself evidence this is a large, error-prone rewrite, not a mechanical one.

**Does this actually break wasm sharing, or is that dead?** Confirmed **not dead** — see the new finding above. `crates/wasm` reuses `crates/core::daemon::Daemon` verbatim today. Changing `Daemon`'s or the tool functions' `Rc<RefCell<...>>` state to `Arc<Mutex<...>>` would force `crates/wasm`'s adapters (`WasmBrowser` et al., all built on wasm-bindgen's single-threaded JS execution model) to either wrap everything in the same `Arc<Mutex<...>>` unnecessarily (dead weight in a runtime that is inherently single-threaded) or fork the shared tool-function signatures between native and wasm — which reintroduces exactly the code-duplication risk this repo's `ports.rs` design was built to avoid.

**Verdict**: technically Option A is what `rmcp`'s examples/tutorials often assume ("just make your service `Send`"), but here it means rewriting the daemon's largest, most stateful crate (browser session management) under time pressure to also prove no new deadlocks were introduced, *and* forcing that redesign onto a Sync target that has no use for it. High risk, large blast radius, contradicts the "Isolate via seam" instinct below.

## Option B — bridge via channel, `!Send` core untouched

**Does this let `crates/core`'s dispatch logic stay untouched?** Yes, by construction. `Daemon::handle_request_bytes` (`daemon.rs:42-49`) is already a pure `&self, bytes -> bytes` async function with no socket or transport awareness — it was written this way specifically to be "independently testable... no socket involved" (`daemon.rs:1-2`). A channel bridge doesn't need to touch this method at all; it just needs a second "front door" that produces `Request`/`Response`-shaped calls into the same `Daemon` instance the Unix-socket `run()` loop already drives, from inside the same `LocalSet`.

Concretely: the `LocalSet` task already owns the `Daemon` and calls `daemon.run(&socket, &sock_path)` in a loop (`main.rs:460`). Add a second concurrent branch to that `LocalSet` (via `tokio::task::spawn_local`, still `!Send`-friendly) that owns an `mpsc::UnboundedReceiver<(Request, oneshot::Sender<Response>)>` and calls `daemon.handle_request_bytes` per received item, replying on the paired `oneshot`. The `mpsc::UnboundedSender` half is `Send` (it only carries `Send` payloads — `Request`/`Response` are plain serde-friendly structs, already `Send` since they're used across the Unix-socket path today) and gets cloned into each per-HTTP-session `S` instance that `rmcp`'s `service_factory` constructs. This exactly matches the "one `S` per session, `Send`, cheap" shape `rmcp` itself expects (see the session-lifecycle finding above) — no exotic bridging needed beyond a channel.

**Duplicated tool-list risk — is there a way to define it once?** Yes, and the shape is already half-built. Today: `ThinClient`'s `#[tool_router]` block (`thin_client.rs:91-...`, one `#[tool(name=..., description=...)]` method per tool, calling `call_daemon`) is the *only* place tool name, description, and typed input/output schema live together. `Daemon::register` calls in `run_daemon` (`main.rs:100-457`) are a second, separate list — but they only carry `&'static str` tool names and closures, no schema/description (those live in `stapler_mcp_core::schema` via `schemars`, already shared). The fix is **not** to write a third `ServerHandler` for HTTP; it's to make `ThinClient`'s existing `#[tool_router]`-derived struct the *one* MCP-facing type, and give it two constructors/call paths depending on transport:
- stdio path (unchanged): `call_daemon` opens a Unix-socket connection per call (current behavior, kept per requirements.md's "Out of Scope: decommissioning stdio").
- HTTP path (new): a sibling constructor whose `call_daemon`-equivalent sends `(Request, oneshot::Sender<Response>)` down the shared `mpsc::UnboundedSender` instead of dialing a socket.

Both share the identical `#[tool_router]` block — the 23 `#[tool]` methods, their `Parameters<...>`/`Json<...>` signatures, names, and descriptions — by parameterizing only the "how do I reach the daemon" seam (a small trait, e.g. `DaemonTransport { async fn call(&self, tool: &str, params) -> Result<Value, String> }`, with a `SocketTransport` impl (today's `call_daemon`) and a `ChannelTransport` impl (new)). This reduces "three copies of the tool list" to **one** `#[tool_router]` definition plus one small transport trait with two thin impls — no tool-schema duplication, and adding a 24th tool touches exactly the places it touches today (the `#[tool_router]` block, `Daemon::register`) plus nothing new.

**Session semantics**: `rmcp`'s per-session `S` is cheap (a couple of `Arc`/channel-sender clones), so `LocalSessionManager`'s in-memory per-session bookkeeping (SSE stream, session ID) stays entirely inside `rmcp`'s `Send` HTTP layer and never touches the `!Send` daemon state directly — every session's tool calls funnel through the single `mpsc` channel into the single `LocalSet`-confined consumer, which serializes access to `Daemon`/`NativeBrowser` exactly as the Unix-socket path already does today (one connection accepted, handled, then the loop continues — see `daemon.rs:87-97`). Concurrent HTTP sessions get concurrent *requests in flight* (multiple in-flight calls queued on the channel) but the actual `Daemon`/browser-pool mutation still happens one `.await`-yielded step at a time on the single `LocalSet` thread, preserving the same effective serialization the Unix-socket path already relies on for the browser pool's single-instance invariant — no new invariant to design or prove.

## Option C — other rmcp-suggested patterns

No `examples/` directory ships in the `rmcp-2.2.0` crate tarball (checked: `find` under the registry path shows only `src/` and `tests/`), so there is no first-party bundled example of wrapping a `!Send` inner service. The crate's own doc comments and its `local` feature (discussed above) are the only textual guidance rmcp ships, and they point at the same conclusion Option B reaches independently: `rmcp`'s `local` feature exists to let a `Service` impl itself be `!Send` for transports that don't need a `Send` boundary (stdio, presumably a future wasm MCP transport) — but `StreamableHttpService` was deliberately built assuming per-session, `Send`, spawnable service instances, because that's what `tokio::spawn` + hyper's connection model requires. There is no rmcp-blessed way to attach a single shared `!Send` service directly to the HTTP transport; a per-session `Send` facade (which is what both `ThinClient` today and Option B's proposed shared-router facade already are) is the pattern the crate itself assumes.

## Recommendation: Option B (channel bridge), reusing `ThinClient`'s tool router as the single source of truth

**Why not A**: the `Arc<Mutex<...>>` rewrite is large (65+ call sites in a 3466-line file, unverified for lock-ordering safety without a full read), forces an unwanted change onto the wasm adapter that has no use for `Send` (confirmed live dependency, not dead code), and doesn't change what's ultimately required anyway — `rmcp`'s `StreamableHttpService` wants a fresh, cheap, `Send` `S` per session regardless of what's behind it, so "make the whole daemon `Send`" buys nothing that a thin `Send` facade doesn't already buy at far lower risk.

**Why B**: it leaves `crates/core::daemon::Daemon` and every `crates/native`/`crates/wasm` port implementation completely untouched — zero risk to the wasm build, zero new deadlock surface, and the exact `Daemon::handle_request_bytes` unit-test seam described in its own doc comment (`daemon.rs:1-2`) keeps working unmodified. It also directly matches the shape `rmcp` itself expects (fresh, cheap, `Send`, per-session `S`), rather than fighting the framework.

**Shape of `run_daemon` after the change** (prose, not code): `run_daemon` still builds the `!Send` `Daemon` and registers all 23 tools exactly as it does today (`main.rs:100-457` unchanged). Two new pieces get added, both spawned onto the same `LocalSet`/`current_thread` runtime so nothing crosses a `!Send` boundary improperly:

1. A **channel-consumer task** (`spawn_local`) that owns the `mpsc::UnboundedReceiver<(Request, oneshot::Sender<Response>)>` and loops calling `daemon.handle_request_bytes`-equivalent (or a thin wrapper taking a typed `Request` directly instead of bytes, to skip a redundant serialize/deserialize round trip that the Unix-socket path needs but this in-process one doesn't) — replying via the paired `oneshot`.
2. An **HTTP-listener task**. Because hyper's HTTP server itself wants a `Send` future graph, this most likely needs `tokio::task::spawn` (not `spawn_local`) for the axum/hyper accept loop — which means the daemon binary needs *both* the existing `current_thread` runtime driving the `LocalSet` (for `Daemon`/`NativeBrowser`) *and* a way to run `Send` tasks concurrently with it. The cleanest fit given the existing `main.rs:32-42` runtime setup is: keep the single `current_thread` runtime, and note that `tokio::task::spawn` **does still work on a `current_thread` runtime** — it just runs the spawned `Send` future on that same single OS thread, cooperatively multitasked with the `LocalSet` tasks (current_thread runtimes execute both `spawn` and `spawn_local` work on one thread; the `Send` bound on `spawn` exists for API uniformity with the multi-threaded runtime, not because current_thread demands cross-thread movement). This means **no second runtime, no cross-runtime channel, no separate thread pool** is needed — the entire "second runtime" contingency requirements.md's Rabbit Holes section warns about is avoidable. Axum's `serve(...)` future and the `LocalSet`'s tasks both run cooperatively on the one `current_thread` executor.

New module: something like `crates/cli/src/http_server.rs` (or a new small module in `crates/core` if the schema/router-sharing needs core-level types — likely stays in `crates/cli` since `rmcp::ServerHandler`/`tool_router` machinery is already cli-only) holding: the axum router wiring `StreamableHttpService` with a `LocalSessionManager`, the bearer-token auth middleware/extractor, and the `service_factory` closure that constructs a fresh `ThinClient`-equivalent (renamed/generalized, e.g. `McpRouter`, parameterized over the new `DaemonTransport` trait) per session, holding a clone of the `mpsc::UnboundedSender`.

**Tool-list single source of truth**: lives where it already effectively lives — the `#[tool_router]` block, moved (or left in place and `use`d) so both `run_thin_client` (stdio, `SocketTransport`) and the new HTTP path (`ChannelTransport`) construct the same router type with different transport implementations. `Daemon::register` in `run_daemon` remains the second (not third) list — the actual handler *implementations*, which is a different concern (business logic vs. protocol-facing schema) and was never proposed to merge with the router.

## Integration points

- **`mcp-servers.json`**: per requirements.md's Success Metrics, consumer machines would add `{"type": "http", "url": "http://127.0.0.1:<port>/mcp", "headers": {"Authorization": "Bearer <token>"}}` entries alongside (not replacing) the existing stdio `command`/`args` entries, per the "keep stdio available" Out-of-Scope decision. This repo's own `mcp-servers.json`/README would need the new entry documented; `stapler-scripts/llm-sync` propagation to Gemini/OpenCode/Antigravity is explicitly flagged out of scope in requirements.md and stays that way here — no new finding changes that.
- **systemd/launchd lifecycle**: the channel-bridge design doesn't change the lifecycle story requirements.md already scoped (a systemd user unit / launchd agent template is still needed, since HTTP serving requires the daemon to be running *before* any client connects — no thin client's `ensure_daemon` auto-spawn exists on the HTTP path by design, since HTTP clients don't spawn processes). This is unaffected by the Option A vs. B choice.

## Data flow / consistency: does HTTP change the browser pool's single-instance invariant?

No, and the channel-bridge design is exactly what preserves that without new work. Today, the invariant is upheld structurally: exactly one `NativeBrowser` (`Rc<NativeBrowser>`, `main.rs:88-94`) exists per daemon process, and every Unix-socket connection's tool call reaches it through the same single `LocalSet`-confined `Daemon::dispatch` call path, one connection handled at a time in `Daemon::run`'s loop (`daemon.rs:87-97`) — concurrency across Unix-socket clients today is already serialized at the daemon's accept-loop granularity, not truly parallel. Under Option B, HTTP sessions add a layer of *client-side* concurrency (multiple sessions can have requests in flight simultaneously, queued on the `mpsc` channel) but the *single consumer* draining that channel and calling into `Daemon`/`NativeBrowser` is still exactly one `LocalSet` task — so the effective serialization the browser pool currently relies on (informally, via the `!Send`/single-thread design rather than explicit locking) is preserved unchanged. This is worth stating explicitly in the plan phase as a design invariant to test (concurrent HTTP sessions hammering a stateful browser tool, per requirements.md's own Success Metric), but it requires no new mechanism beyond "the channel has one consumer."

## Disposition: Isolate via seam

`crates/cli/src/main.rs::run_daemon` and `crates/core/src/daemon.rs` are not a hotspot to refactor first, nor safe to silently extend without a new abstraction. `daemon.rs` is deliberately small (170 lines) and already has the right seam (`handle_request_bytes`, a pure function with no transport coupling) — that seam is *why* Option B is cheap: it needs a new front door, not a rewrite of what's behind it. `run_daemon` in `main.rs` is long (491 lines) but its length is repetitive tool-registration boilerplate, not entangled logic — SOLID/DDD-boundary violations aren't the risk here; the risk is purely the `Send`/`!Send` transport mismatch, which is infrastructure/transport work as the prompt frames it. Recommend: **isolate via seam** — add the channel-bridge + shared tool-router facade as new, additive modules, leave `Daemon`'s dispatch core and every `crates/native`/`crates/wasm` port implementation untouched.
