## Blockers from iteration 1 — both RESOLVED, with residual gaps noted as new Concerns below

- [x] **Blocker 1 (SIGTERM/shutdown Rc-ownership race) — RESOLVED for the failure mode originally described.** The plan now gives every blocking loop a real cancellation path off a single `Daemon`-owned `CancellationToken` (Domain Glossary; Task 2.1.1b), reached through one funnel method `Daemon::request_shutdown` called identically by the `SHUTDOWN_TOOL` dispatch arm and the SIGTERM handler (Task 2.1.1b, Task 5.1.1a). `Daemon::run_cancellable` (Task 2.1.1d) and the bridge consumer (Task 2.2.1c) both `tokio::select!` against that token instead of only re-checking a flag after their next event. `run_daemon`'s single `tokio::join!` (Task 2.2.1d) awaits the accept loop, the bridge consumer, and (if enabled) the HTTP server together, each grace-timeout-bounded; `shutdown_cleanup` is extracted and called exactly once, after that join, from exactly one place. `std::process::exit()` is explicitly removed from the SIGTERM path (Task 5.1.1a: "does **not** call `std::process::exit()`"; Task 2.2.1d: "no `std::process::exit` anywhere in this path, so `main` returns and destructors run") — the SIGTERM handler itself is reduced to "log, call `request_shutdown()`, nothing else," matching the repair's claim.
  Verified the wasm-noninterference claim directly: `crates/wasm/src/lib.rs:257` today reads `let run_result = daemon.run(&socket, &sock_path).await;` — the plain, pre-existing method, with no cancellation awareness. The plan's Domain Glossary row for `Daemon::run_cancellable` states "`Daemon::run` itself is left completely unchanged... `crates/wasm/src/lib.rs:257`'s existing call site needs no edit," and Task 2.1.1d confirms `run_cancellable` is a new sibling method, not a modification to `run`. This matches the real file exactly (right line, right call). Story 2.1.1's acceptance criteria also make the sole-ownership claim concrete and testable (`Rc::get_mut(&mut browser)` succeeds because every `Rc`-holding task has exited via the join before `shutdown_cleanup` runs) rather than just asserting it.
  Tracing the actual ownership chain confirms this holds for the **common-case** shutdown: `run_cancellable` only borrows `&self` (no extra owned clone to outlive the loop), the bridge consumer's `Rc<Daemon>` clone is dropped when its joined task exits, and per-HTTP-session `McpRouter<ChannelTransport>` instances hold only a cloned `mpsc::Sender`, never an `Rc<Daemon>`/`Rc<NativeBrowser>` directly (Task 3.1.1a) — so by the time the join resolves, the `Rc<Daemon>` passed into `shutdown_cleanup` is genuinely the last one, and dropping it there frees the handler closures' captured `Rc<NativeBrowser>` clones before `Rc::get_mut(&mut browser)` runs. See new Concerns below for two narrower, non-blocking gaps this tracing surfaced.

- [x] **Blocker 2 (`DaemonTransport` missing `Send` bound) — RESOLVED.** The Domain Glossary's `DaemonTransport` row and Task 1.2.1b both now specify the exact fixed signature: `fn call(&self, tool: &'static str, params: serde_json::Value) -> impl std::future::Future<Output = Result<serde_json::Value, String>> + Send` — an RPITIT with an explicit `+ Send` bound, citing `rmcp-macros-2.2.0/src/tool.rs:343-383` (the same citation verified in iteration 1) and `tower.rs:571-577` for why `local`/`#[tool(local)]` isn't usable here. This is exactly the remediation iteration 1 recommended, and it does satisfy the `Send` requirement: the compiler can now prove `Box::pin(async move { ...self.transport.call(...).await... })` is `Send` for any `T: DaemonTransport` because the bound lives on the trait itself, not just on concrete impls. Task 1.2.1a's spike is explicitly rewritten to exercise this literal trait shape ("using the literal `Send`-bounded `DaemonTransport` shape... a trait without the `Send` bound would pass the spike while hiding the real compile error"), closing the gap iteration 1's Concern 1 flagged about the spike not necessarily reproducing this exact risk.

## Concerns

- [ ] **New (introduced by the repair): the SIGTERM listener task's own `Rc<Daemon>` clone is not part of `run_daemon`'s `tokio::join!` (Task 2.2.1d), so the plan's "not a race, by construction" claim (Story 5.1.1's acceptance criteria) rests on an unstated assumption about tokio's single-threaded scheduling order rather than an explicit guarantee.** Task 5.1.1a's listener task must hold its own `Rc<Daemon>` clone to call `request_shutdown()` after `.await`ing the signal (required since it's `!Send` and must run via `spawn_local`, not `tokio::spawn` — see nitpick below). That clone is dropped when the listener task's future completes, but nothing in the plan makes that completion happen-before `shutdown_cleanup`'s `drop(daemon)`, because this task's `JoinHandle` is never joined anywhere. In practice this is very likely safe — the listener task has no further `.await` after calling `request_shutdown()`, so it completes in the same poll that fires cancellation, well before the other three loops (which each need at least one more wakeup to notice cancellation and unwind) resolve their own joined handles — but the plan doesn't state this as a documented invariant, and "genuine sole ownership... not a race, by construction" is a strong claim to leave resting on implicit scheduler timing.
  **Recommendation**: either capture and include the SIGTERM listener task's `JoinHandle` in Task 2.2.1d's `tokio::join!` (cheap — the task is already tiny and short-lived), or add one sentence to Story 5.1.1/Task 5.1.1a explicitly stating why its omission from the join is safe (single-poll completion on a cooperative single-threaded runtime).

- [ ] **New (introduced by the repair): the grace-timeout backstop in Task 2.2.1d/5.1.1c proceeds to `shutdown_cleanup` on a timeout without aborting the timed-out task, so the sole-ownership guarantee does not hold in exactly the "genuinely stuck task" case it exists to handle.** `tokio::time::timeout(SHUTDOWN_GRACE_TIMEOUT, handle)` returns `Err` when it fires, but the underlying spawned task (e.g. a hung bridge consumer blocked on a stuck CDP call) keeps running in the background — it is not cancelled. Task 2.2.1d says to "log distinctly and proceed to cleanup anyway," which means `shutdown_cleanup`'s `Rc::get_mut(&mut browser)` can fail in exactly this branch, silently skipping the reaper-abort/`browser.close()` sequence — the same symptom (not the same root cause) as iteration 1's Blocker 1. This is a materially narrower, already-flagged-as-residual scenario (Task 5.1.1c calls it out as "the *residual* risk... a handler that's actually hung"), not a regression of the common-case fix, so it doesn't warrant reverting the verdict to BLOCKED — but the acceptance criteria's blanket "it succeeds (returns `Some`)... not a race, by construction" phrasing should be scoped to the non-timeout case, since it currently reads as an unconditional guarantee.
  **Recommendation**: call `.abort()` on any handle that times out, immediately after logging, before proceeding to `shutdown_cleanup` — this doesn't guarantee the aborted task's stack frame (and its `Rc` clone) drops synchronously either, but it at least signals intent and stops new work from starting on it, and the acceptance-criteria wording should note this branch as accepted-degraded rather than implying full sole ownership always holds.

- [ ] **Carried forward from iteration 1, still open — `BridgeMessage` (Task 2.2.1a) is a raw tuple type alias rather than a small named struct.** Domain Glossary line 21 still defines it as `(Request, oneshot::Sender<Response>)`, unchanged from iteration 1. Still a minor readability nitpick per the original note (every use site destructures it positionally already), not upgraded here.

- [ ] **Carried forward from iteration 1, still open — `ChannelTransport::call`'s dropped-sender/closed-channel error path (Task 2.3.1a) is now even more clearly a defensive-only path given `std::process::exit` is fully removed from the SIGTERM path.** Worth the one-line comment iteration 1 suggested, noting it's reachable only via an actual task panic, not normal shutdown.

## Nitpicks

- Task 5.1.1a's wording ("Spawn a `tokio::signal::unix::signal(...)` listener task") doesn't explicitly say `spawn_local`, unlike Tasks 2.1.1d and 2.2.1c which do. Since the task must capture an `Rc<Daemon>` clone across an `.await`, it will fail to compile under `tokio::spawn` (`Send` required) — a self-correcting omission at implementation time, but worth matching the explicit `spawn_local` callout used elsewhere in the plan for consistency.
- The "one shared tool-list" claim (Pattern Decisions row 1) remains well-supported: Task 8.1.1a still mechanically compares `McpRouter::<SocketTransport>::registered_tools()` against `McpRouter::<ChannelTransport>::registered_tools()`. Unchanged from iteration 1, noted again here as still a positive, not a finding.
- Tech Debt Disposition's `main.rs::run_daemon` row (iteration 1's Concern 2) was rewritten to directly address the Rc-sharing implications the new concurrent tasks introduce, and a new fourth row was added for `Daemon::run`'s accept loop disposition — both concerns from iteration 1 were substantively addressed as a byproduct of the blocker repair, not just left as prose promises.
