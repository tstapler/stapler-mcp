# Pre-mortem: mcp-streamable-http
**Date**: 2026-09-14

Scope note: `architecture-review.md` and `adversarial-review.md` already carry five residual CONCERNS (channel saturation/timeout policy, no panic recovery in the bridge-consumer task, no latency-regression benchmark, an unstated scheduling assumption in the SIGTERM listener's ownership chain, and a grace-timeout backstop that doesn't abort a timed-out task). This pre-mortem treats those as known inputs, not rediscoveries, and asks the sharper question: of everything that could go wrong, what's actually most likely to bite in the first month of Tyler using this daemon for real browser-automation work? Two of the five items below sharpen already-flagged concerns with a mechanism the reviews didn't name (Daemon::run's own accept loop shares the exact same serialization bottleneck as the bridge channel — verified by reading `crates/core/src/daemon.rs:80-97`); three are new.

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | A single slow/hung tool call (a real browser navigate to a page with an infinite JS loop, a stalled CDP command, a dialog blocking the page) blocks *every* concurrent session's tool calls indefinitely — not a new bug, but the HTTP migration's entire purpose (making concurrent multi-session/subagent usage cheap) multiplies how often real usage collides with it | All Claude Code sessions and subagents across the daemon simultaneously stop responding to any tool call, with nothing in `daemon.log` beyond at most one generic "queued >250ms" line — indistinguishable from "just slow" | Add a bounded per-request timeout inside `Daemon::handle_request` or `DaemonTransport::call` itself (not only an axum-layer timeout, since `Daemon::run`'s Unix-socket accept loop shares the identical single-threaded serialization point, verified at `crates/core/src/daemon.rs:80-97`), so one stuck call fails with a specific error instead of starving every other caller forever; add a Phase 8 test that intentionally hangs one handler and confirms other concurrent calls still complete or time out | P1 |
| 2 | A tool-handler panic inside the bridge consumer's `spawn_local` task kills that task permanently; the paired `mpsc::Receiver` drops, and every subsequent `ChannelTransport::call` fails with a generic "channel closed" error — the HTTP transport is silently and completely dead until a manual daemon restart, while the Unix-socket path (a separate code path, unaffected) keeps working fine, making the failure look like "just my session" rather than "the whole HTTP transport is gone" | Every HTTP-originated tool call across every session starts failing with the same opaque "channel closed" error at the same moment; nothing in `daemon.log` names "bridge consumer panicked" as the cause, and `stapler-mcp --status` still reports the daemon as running (it only pings the Unix socket) | Wrap the bridge consumer's per-request dispatch in `catch_unwind` (or otherwise convert a handler panic into an `Err` reply instead of task death); log a distinct line naming this failure mode; add a Phase 8 test that panics a registered handler and confirms the HTTP transport keeps serving subsequent requests afterward | P1 |
| 3 | Claude Code's real reconnect/retry behavior against a restarting daemon, verified by exactly one manual spot-check before ship (Task 9.1.1a) against a clean restart, doesn't hold for the restart triggers actually seen over a month: `Restart=on-failure` after a panic (item 2), an OOM-kill of a memory-hungry Chrome session, a manual `stapler-mcp --daemon` restart during active development, or a laptop sleep/wake dropping the TCP connection | Mid-session, tool calls start silently erroring or hanging with an opaque transport error, and there's no documented recovery step the user would find in the moment (`NOTES.md` isn't consulted mid-incident) | Broaden Task 9.1.1a to also cover a `kill -9` restart and a sleep/wake cycle, not just a clean restart; put whatever recovery procedure is found (even if it's just "restart Claude Code") directly into the Troubleshooting section (Task 7.2.1c), not only `NOTES.md` | P2 |
| 4 | The bearer token leaks into a git-tracked or `llm-sync`-mirrored file despite the plan's manual-copy-paste design (Task 7.2.1d), because that design relies entirely on human discipline across a multi-machine setup with no automated guard — `mcp-servers.json` is git-tracked and mirrored to Gemini/OpenCode/Antigravity by `stapler-scripts/llm-sync` per `requirements.md`'s own Users/Consumers section | A routine `git diff`/`git log -p` review turns up a live 64-hex-char token committed weeks earlier, or it's found only after `llm-sync` has already mirrored it into another tool's config directory | Add a pre-commit or CI grep check (reusing existing secret-scanning tooling if `dotfiles` has one) that fails if `mcp-servers.json` or its llm-sync-mirrored copies contain a string matching the token's format, rather than relying solely on the documentation warning | P2 |
| 5 | Port `47439` isn't actually free on one of Tyler's several real machines (explicitly unresolved in `plan.md`'s Unresolved Questions, owner: Tyler, `lsof -i :47439` not yet run) — the daemon correctly degrades to stdio-only rather than crashing, but that degrade is silent enough (log-only) that a machine whose `mcp-servers.json` was switched to `http` transport sees every tool call fail with connection-refused, with the real cause sitting in `daemon.log` where nothing points the user to check it | Every tool call on that one machine fails immediately after switching to HTTP; the obvious first move ("restart Claude Code") doesn't help, and there's no direct link from the symptom to "check daemon.log for a port-in-use line" | Have `--status` or `--print-config` proactively surface a recent "port already in use" log line instead of requiring the user to already know to grep `daemon.log`; resolve the open `lsof -i :47439` check on all target machines before Story 5.2.1 ships the unit templates | P3 |

## P1 Items (address before implementation)
- [ ] Failure #1 — add a bounded per-request timeout at the `Daemon::handle_request`/`DaemonTransport::call` layer (shared by both the Unix-socket and bridge-channel paths, since both share the same single-threaded serialization bottleneck) and a Phase 8 test proving one hung call doesn't starve concurrent callers.
- [ ] Failure #2 — wrap the bridge consumer's per-request dispatch in `catch_unwind`, add a distinct "bridge consumer panicked" log line, and add a Phase 8 test proving the transport survives a handler panic.

## Summary
5 failure modes: 2 P1, 2 P2, 1 P3.

Top failure mode: the daemon's dispatch core (`Daemon::run`'s accept loop *and* the new bridge consumer) is fully single-threaded and serial with no per-request timeout, so one hung real-world browser call (the exact kind this daemon exists to make) freezes every concurrent session at once — a pre-existing bottleneck that this migration's own goal (frictionless concurrent multi-session usage) makes far more likely to actually get hit in production.
