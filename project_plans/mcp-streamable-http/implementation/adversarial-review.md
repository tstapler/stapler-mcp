# Adversarial Review: mcp-streamable-http

**Date**: 2026-09-14 (iteration 2 — re-review of the repair pass targeting iteration 1's 2 blockers + Concern 4)
**Verdict**: CONCERNS

## Resolved in this iteration

- [x] **Blocker 1 (missing `tokio` `"signal"` feature)** — confirmed fixed. Task 1.1.1b (`plan.md:156-158`) now explicitly adds `"signal"` to `crates/cli/Cargo.toml`'s `tokio` features list, and Story 1.1.1's acceptance criteria (`plan.md:147`) states the same edit with a before/after diff. The task text also directs a post-edit `cargo build -p stapler-mcp` check for any other transitively-required feature rather than asserting the list is exhaustive by assumption.
- [x] **Blocker 2 (SIGTERM doesn't synchronize with in-flight work)** — confirmed fixed, all three original sub-problems addressed:
  1. **Graceful HTTP shutdown now awaited before exit**: Task 5.1.1b (`plan.md:435-437`) has `run_http_server` build its graceful-shutdown future from `daemon.cancellation_token()`, spawns it via `tokio::task::spawn`, and captures the `JoinHandle` — which Task 2.2.1d's single `tokio::join!` awaits (bounded by `SHUTDOWN_GRACE_TIMEOUT`, Task 5.1.1c) before cleanup runs. The plan explicitly distinguishes "token cancelled" from "HTTP server finished flushing in-flight responses" as two separately-awaited events (`plan.md:436`).
  2. **Bridge consumer awaited before `browser.close()`**: Task 2.2.1c (`plan.md:284-286`) captures the bridge consumer's `spawn_local` `JoinHandle`; Task 2.2.1d joins it (grace-timeout-bounded) alongside the accept loop and HTTP server before calling `shutdown_cleanup`. The consumer's `select!` only checks cancellation at the top of its loop, so an in-progress `daemon.handle_request(req).await` is allowed to finish before the task exits — no close-while-in-use race by construction.
  3. **SIGTERM reuses the same join/cleanup as the SHUTDOWN_TOOL-RPC path**: Task 5.1.1a (`plan.md:431-433`) now has the SIGTERM handler do nothing but log and call `daemon.request_shutdown()` — no independent cleanup copy, no `std::process::exit()`. `request_shutdown` (Task 2.1.1b) is the same method the `SHUTDOWN_TOOL` dispatch arm now calls (`daemon.rs:54-57` updated per that task), so both triggers cancel the identical `CancellationToken` and fall through to the identical, single `tokio::join!` → `shutdown_cleanup` sequence (Task 2.2.1d, called "from exactly one place"). `main` returns normally (exit code 0) instead of calling `process::exit`.
  - **Phase 8 test added**: Epic 8.3/Story 8.3.1/Task 8.3.1a (`plan.md:611-622`) sends SIGTERM mid-request against a real HTTP-enabled daemon and asserts the in-flight request either completes or fails with a clean, assertable error (never a hard-killed connection/hang), plus asserts `daemon.log` shows exactly one cleanup sequence's worth of log lines — directly verifying the single-shutdown-path claim, not just the process exiting.
- [x] **Concern 4 (SIGTERM cleanup duplicated by line reference)** — confirmed fixed. `shutdown_cleanup` is now a named, defined function (Domain Glossary, `plan.md:27`; extraction spec'd in Task 2.2.1d, `plan.md:288-290`) called from exactly one call site — immediately after `run_daemon`'s single `tokio::join!` completes — regardless of which trigger (SIGTERM or `SHUTDOWN_TOOL`) caused the shutdown. Task 5.1.1a explicitly notes it removes the SIGTERM handler's former independent copy of this sequence in favor of triggering the shared one.

No new problems were introduced by the redesign that rise to blocker severity: the `Option<JoinHandle>` handling for the HTTP arm of `tokio::join!` when HTTP is disabled (Task 3.2.1a, `plan.md:352-354`) is described only at "skipped/treated as already-complete" granularity rather than exact code, but this is ordinary plan-level detail (e.g. an `async move { if let Some(h) = http_handle { h.await } else { Ok(()) } }` wrapper), not a design gap.

## Concerns

*(carried forward unchanged from iteration 1 — out of scope for this repair pass)*

- [ ] **No timeout/admission-control policy for a saturated bridge channel beyond a single 250ms warning log, and no test exercises the channel at its bound.** Task 6.1.1b logs once when `bridge_tx.send(...).await` exceeds 250ms, then continues waiting indefinitely with no further logging and no upper bound. A genuinely stuck daemon-core request (e.g. a hung CDP/browser call) would queue every subsequent HTTP request behind it forever, each hanging with only one generic log line ever emitted and no server-side request timeout (no `tower::timeout::TimeoutLayer` or equivalent appears anywhere in the axum wiring) to fail fast and return a `503`/`504` to the caller. Separately, no task in Phase 8 actually bursts >`BRIDGE_CHANNEL_CAPACITY` (64) concurrent requests to verify the backpressure log line and eventual-completion behavior Story 6.1.1's acceptance criteria describe — Phase 8's concurrency coverage (Task 8.1.2a) only exercises 2 concurrent calls. — **Recommendation**: add a bounded server-side request timeout on the axum router, and a Phase 8 task that saturates the channel (>64 in flight) to verify both the backpressure log and that queued requests still resolve (or time out cleanly) rather than hanging forever.

- [ ] **No supervision or recovery if a tool call panics inside the bridge consumer task, and no distinct log line marking that failure mode.** The bridge consumer (Task 2.2.1c) is its own `spawn_local` task; Tokio isolates a panic to that task's boundary, so a panicking tool handler kills only the bridge consumer — but nothing detects or restarts it. Once it's dead, the paired `mpsc::Receiver` drops, so every subsequent `ChannelTransport::call` fails with a generic "channel closed" error. The entire HTTP transport is then silently and permanently broken until a full daemon restart, with no log line distinguishing "bridge consumer died" from any other failure — the Observability Plan (Phase 6) has no line item for this. — **Recommendation**: wrap the bridge consumer's per-request dispatch in `catch_unwind` (or otherwise convert a handler panic into an `Err` reply rather than task death), and/or log distinctly and consider auto-respawning the consumer task if it exits unexpectedly.

- [ ] **Requirements.md's Non-functional "should not regress the current per-call latency of a Unix-socket round trip" has no corresponding verification task.** `research/pitfalls.md` §5 explicitly flagged this as "worth benchmarking... rather than assuming SSE's overhead is negligible," and ADR-0002 picks `json_response: true` on rationale grounds, but no task in Phase 8 (Testing) or Phase 9 (Manual verification) actually measures HTTP per-call latency against the existing Unix-socket baseline. — **Recommendation**: add a lightweight benchmark/comparison task (even a manual one in Phase 9, mirroring Task 9.1.1's pattern) comparing a representative tool call's latency over HTTP vs. the existing stdio/socket path.

## Minors

*(carried forward unchanged from iteration 1)*

- `stapler-mcp --status` (Story 7.1.1) isn't named in requirements.md's Scope or Success Metrics sections — it's well-justified by `research/ux.md`'s diagnosability argument and is low-risk, but it's scope not directly traceable to the requirements doc; `--print-config` (Story 7.1.2) is better-justified since it's load-bearing for ADR-0002's token-distribution decision.
- Task 4.1.1c's `generate_or_load` treats any non-empty token file as valid without validating length/format; a process crash mid-write (narrow window) could leave a truncated file that's silently accepted as a valid token on the next daemon start.
- Task 1.1.2a pins `rand = "0.9"` for `OsRng`/`RngCore::fill_bytes` (Task 4.1.1c) without confirming which feature flag rand 0.9 requires for `OsRng` — worth a quick check during Task 1.1.2a/c rather than discovering it at `cargo build` time.
- Task 3.1.1d's `TcpListener::bind` doesn't mention `SO_REUSEADDR` or discuss whether a same-port rebind shortly after a hard-killed daemon could hit a spurious `EADDRINUSE` from lingering socket state — likely a non-issue for a bare listening socket on Linux, but this codebase has no prior TCP-port-binding precedent to lean on (per `research/features.md` §3's own note that the Unix-socket design was chosen specifically to avoid port-conflict risk), so it's worth a one-line confirmation rather than an assumption.
