# Pre-mortem: read-website-daemon-recovery
**Date**: 2026-10-29

Scenario: the PR merged, and within a month the parallel-subagent research flow still fails or a new regression appeared. Claims below are tagged VERIFIED (code read or command run in this worktree / on this machine) or INFERRED.

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | The liveness ping is itself a request in the daemon's serial queue. A tail caller's 2 s ping (`DIAL_TIMEOUT`) can only succeed when the queue ahead of it drains in under 2 s. Each timed-out ping is abandoned and the retry goes to the back of the queue. With 5-10 parallel `read_website` calls (the original use case), tail callers burn the whole 45 s startup budget in `ensure_daemon`, never send their real request, and fail with "reachable but did not answer in time". The "Connection refused" text goes away but the user-visible failure remains. AC1 hides this because its test uses 8 *short* pages. | Subagent tool results like `ensure daemon: timed out (daemon reachable...)` under fan-out, while `daemon.log` shows the daemon healthy and serving. | Make a busy daemon count as alive: in `ensure_daemon`, treat `PortError::Timeout` from the ping as "alive, proceed" (return `Ok(())` after at most one short re-ping) so the real call queues under `CALL_TIMEOUT` (120 s). Spawn and wait-to-deadline remain only for non-Timeout errors (refused, ENOENT, closed). Update ADR-001, the Story 2.1.1 Given/Then (Timeout case returns `Ok` with 0 spawns, not `Err(Timeout)` at 30 s), and `ensure_daemon_should_return_timeout_without_spawning_after_deadline`. Add an e2e test: one slow in-flight request (local slow HTTP server, as `daemon_ping.rs` does for its mock) while 8 clients run `ensure_daemon` then a real call; all must succeed. | P1 |
| 2 | An old buggy daemon keeps running after merge, so the fix has no effect until it dies. VERIFIED: PID 129763 has run 21 h from a different checkout's `target/release/stapler-mcp --daemon`. `ensure_daemon` pings it successfully and never replaces it. Manual verification of the PR on this machine is also misleading unless that daemon is shut down first. | After merge and upgrade, `daemon.log` still shows `daemon run error: io error: Broken pipe` (VERIFIED: 3 such lines exist today) and the next call sees Connection refused once. | Add to the PR body and the Phase 6 verify checklist: run the `shutdown` tool (or kill the daemon) before manual verification. Optionally note the self-heal: the old daemon dies on its next EPIPE and the new thin-client respawns the new binary. Out of scope for this plan: version check in ping. | P2 |
| 3 | The plan contradicts itself on spawn count, so the implementer ships the wrong half. Story 2.1.1 and test `ensure_daemon_should_spawn_at_most_once_when_pings_keep_failing` say "at most once per call"; Review resolution 3 says allow a second spawn (cap 2) after a Timeout phase. Task 2.1.1a text does not mention it. | Either a failing unit test, or a daemon that dies mid-wait is never respawned by that caller (AC0 flake). | Reconcile before coding: edit Story 2.1.1 and Task 2.1.1a to "spawn on first non-Timeout error; allow one more spawn only if a non-Timeout error follows a Timeout phase; total cap 2". Add a test for that transition. If failure mode 1's prevention is adopted, Timeout returns `Ok`, and this resolution item can be dropped entirely (simpler). | P2 |
| 4 | Listener `accept()` errors stay fatal (task 1.1.1a "leave `accept().await?` untouched"). Under heavy fan-out, transient accept errors (EMFILE/ENFILE with Chrome holding many fds, ECONNABORTED) still make `run_cancellable` return `Err`, and `run_daemon` calls `exit(1)` (VERIFIED `main.rs:964-966`), leaving a stale socket. This is the original symptom via a different trigger. The current log shows only Broken pipe, so the likelihood is moderate, not proven. | `daemon.log` ends with `daemon run error: io error: Too many open files` and the next call needs a respawn. | In `serve_logged`'s sibling accept path, log and retry transient kinds (EMFILE, ENFILE, ECONNABORTED, EINTR) with a short sleep (e.g. 100 ms) and keep fatal for the rest. Keep the `run_should_return_err_when_accept_fails` test, using a non-transient error such as `PermissionDenied`, and add a test that a transient error is retried. | P2 |
| 5 | The e2e tests are flaky or leaky. Asserting `< 30 s` for a cold Chrome start fails on a loaded CI runner. SIGKILL leaves the orphaned ephemeral-profile Chrome running. Failed tests leave daemons running (no cleanup on panic). Daemons spawned via `Command::spawn` without `wait` become zombies, so `libc::kill(pid, 0)` returns 0 for a dead daemon. In-process `join_all` of 8 futures does not model 8 separate thin-client processes. | Intermittent red CI on `daemon_kill_restart` / `daemon_parallel_cold_start`; stray `chrome` and `stapler-mcp --daemon` processes on dev machines. | Use a drop guard that sends `shutdown` (then SIGKILL as fallback) per test. Check liveness via `/proc/<pid>/stat` state != `Z`, or by a failed ping, not `kill(pid, 0)`. Keep AC0's 30 s as the assertion but give the client budget 45 s so the failure message distinguishes slow from broken. Run 8 clients as separate OS processes (or at least a second copy with a shared barrier) in 4.1.1b. Kill the orphaned Chrome in the kill test cleanup. | P2 |
| 6 | A wedged-but-alive daemon is never recovered. With ADR-001 (no spawn on Timeout), a daemon that holds the flock and accepts connections but never answers makes every caller error out. Pre-fix behaviour was no better (the spawned loser exits on the lock), so this is not a regression. | Every call returns the "reachable but did not answer" message; the user must kill the process by hand. | Because the message now names `daemon.log`, include the daemon PID from `daemon.lock` and a `kill <pid>` hint in `ensure_error_message` for the Timeout variant. | P3 |
| 7 | `status_probe` default-method plumbing fails to compile (`impl Future + Send` with `&self` across an await) or the new optional fields break a hard-coded schema expectation. Already flagged by the reviews. | `cargo check` / `tool_schema.rs` fails in Wave 3. | Follow Review resolution 1 (`cargo check` the trait default first; build the `call` future before the `async` block). Run `tool_schema.rs` at the start of Wave 1 task 3.1.2a, not at the end. | P3 |

## P1 Items (address before implementation)
- [ ] Failure #1: replace "wait on Timeout until the startup deadline" with "Timeout means alive; return `Ok` and let the real call queue under `CALL_TIMEOUT`". Update ADR-001, the Story 2.1.1 Given/Then for the Timeout case, tests `ensure_daemon_should_not_spawn_when_ping_times_out_then_recovers` and `ensure_daemon_should_return_timeout_without_spawning_after_deadline` in Task 2.1.1b, and add an e2e fan-out test with one slow in-flight request (Task 4.1.1b). Also add a Known-limits line: the ping/queue interaction was the reason for the change.

## P2 items to fold into plan text before coding
- #3: reconcile "at most once" with Review resolution 3 (or drop resolution 3 if #1's prevention is adopted).
- #4: make transient accept errors non-fatal, or explicitly accept the gap in Known limits.
- #5: add test cleanup guards and a non-`kill(pid, 0)` liveness check to Tasks 4.1.1a-c.
- #2: add the "shut down the old daemon before verifying" step to the PR body and the verify phase.

## Evidence notes
- VERIFIED root cause: `~/.stapler-mcp/daemon.log` lines 368, 370, 414 contain `daemon run error: io error: Broken pipe (os error 32)`; 260 lines say `daemon already running`, which matches the spawn-on-ping-Timeout storm described in F4.
- VERIFIED serial accept loop: `crates/core/src/daemon.rs:183-192` awaits each connection before the next `accept`.
- VERIFIED ping is a full request: `crates/core/src/client.rs:28-57` (`ping` = `call` with write then `read_frame`, both bounded by the same timeout).
- VERIFIED spawner appends to the log and does not truncate it (`crates/native/src/spawn.rs`), so concurrent loser daemons do not erase the winner's log, which the 4.1.1c log assertion relies on.
