# Pitfalls Research: browser-automation

## 1. `chromiumoxide` gotchas

- **Zombie/orphaned Chrome subprocesses on error paths.** This is a well-documented cross-tool problem (chromedp, Puppeteer, Selenium all hit it) rather than a chromiumoxide-specific bug: when the driving process dies or errors *before* explicitly sending a termination signal to the Chrome child (and its zygote/renderer children), the OS-level parent-child link is orphaned and the Chrome process(es) keep running, consuming RAM/CPU indefinitely. The chromedp writeup found that killing "the Go process" doesn't reliably kill Chrome because Chrome forks through intermediate processes, so the fix has to target the process group, not a single PID. **Applies directly here**: `NativeBrowser::close()` (`crates/native/src/browser.rs:38`) is a single `browser.close()` call that must be reached explicitly at shutdown — if the daemon panics, is SIGKILLed, or a bug causes an early-return before shutdown ever runs `close()`, the Chrome process is orphaned with no cleanup path from inside chromiumoxide itself. [Aymeric Beaumet: chromedp zombies](https://aymericbeaumet.com/prevent-chromedp-chromium-zombie-processes-from-stacking/), [Puppeteer zombie processes in production](https://medium.com/@TheTechDude/puppeteer-memory-leaks-crashes-and-zombie-processes-6-months-of-screenshots-in-production-b2ae7e65df3f)
- **`Target.targetCrashed` / tab crash is a CDP-level event, not chromiumoxide-specific.** A `Page` can crash independently of the driving process (OOM, heavy CPU page, renderer crash) — this produces cascading errors like "session deleted because of page crash" downstream of the crash. chromiumoxide exposes the raw CDP `Target` domain events but there is no evidence it auto-recovers a crashed page; the caller must listen for `TargetCrashed`/`TargetDestroyed` and treat the corresponding session as dead. **Applies directly here**: this feature's whole premise is a *persistent* `Page` handle held across multiple tool calls (navigate → click → type → snapshot). If the underlying tab crashes between calls, the next call against that `session_id` will get a CDP error from a dead target — the session map needs a way to detect "this Page's target died" and evict the entry rather than silently retrying against a dead handle. [CDP Target domain](https://chromedevtools.github.io/devtools-protocol/tot/Target/), [Selenium tab-crash issue](https://github.com/SeleniumHQ/selenium/issues/12628)
- **AX-tree API surface confirmed by prior research (`research/stack.md`) but has real footguns**: `getFullAXTree` needs an explicit `frameId` or it returns only the root node; `queryAXTree` needs `backendNodeId` scoping or can return empty; and Chrome builds the AX tree lazily, so the very first snapshot right after `navigate` can come back empty/partial unless primed or the load event is awaited first. This is already flagged in stack.md but is a first-order pitfall specifically for the `navigate` → `snapshot` sequence in scope.
- **No confirmed chromiumoxide-specific regression for long-lived multi-`Page` sessions was found**, but community sentiment treats it as less battle-tested than Puppeteer/Playwright for exactly this scenario (holding many tabs open across long spans, concurrent access). Treat "hold 2+ persistent pages across an `.await` boundary spanning multiple tool calls, for minutes" as an empirically-unverified assumption to smoke-test early, not a given.

## 2. General headless-Chrome automation pitfalls

- **Navigation race / "Execution context was destroyed, most likely because of a navigation."** This is the single most common headless-Chrome automation bug across Puppeteer/Playwright/Browsershot, and it maps directly onto this feature's `click`/`type` operations: if a `click` triggers navigation (e.g. clicking a submit button or a link), any DOM read or further `evaluate` against the **old** execution context after navigation starts will throw — the classic mistake is calling `click()` then reading page state without first setting up a navigation-wait *before* triggering the click. The pattern this codebase's `click` implementation must follow: begin listening for navigation *before* firing the click, not after, or accept that some clicks are "fire and check separately." A locator/element handle obtained from a pre-navigation snapshot is invalid after the page navigates and must not be reused — the caller-facing implication is that a `snapshot` taken before a `click` cannot be assumed valid for a subsequent `click`/`type` call if the intervening action caused a navigation. [screenshotone.com writeup](https://screenshotone.com/blog/puppeteer-execution-context-was-destroyed-most-likely-because-of-a-navigation/), [AppSignal Puppeteer mistakes](https://blog.appsignal.com/2023/02/08/puppeteer-in-nodejs-common-mistakes-to-avoid.html)
- **Detecting "this became a different page" is a first-class problem, not an edge case.** Distinguishing "the click did nothing," "the click triggered an in-page SPA route change," and "the click triggered a real navigation" requires different waiting strategies per case (`waitForNavigation` is *wrong* when no navigation happens — it will just hang or timeout). The port's `click` operation needs an explicit policy here (e.g. best-effort short wait for either a navigation event or DOM settle, then return current URL so caller can detect a page changed) rather than assuming one universal wait strategy works for all clicks.
- **Zombie processes and headless/server-environment flag gotchas** (no X server, sandbox requirements) are the standard operational risk class for any headless-Chrome deployment; this repo's `NativeBrowser::launch()` uses `BrowserConfig::builder().build()` with no explicit flags today (`crates/native/src/browser.rs:18`), so this is an existing baseline risk (not new to this feature) but worth calling out since a long-running daemon amplifies the cost of Chrome failing to launch or crashing repeatedly under a restrictive container (missing `--no-sandbox`/missing shared-memory size in Docker, etc.).
- **Long-lived sessions grow memory over time** — every open tab/page holds its own renderer process and JS heap; the existing "fresh tab per call, close immediately" design (documented in `stack.md` for both adapters) avoided this, but the new persistent-per-session tab model reintroduces classic long-session memory growth risk, especially if the reaper interval is too generous or sessions accumulate faster than they idle out.

## 3. Reaper / idle-timeout pitfalls, tokio-specific

- **TOCTOU between reaper eviction and a concurrent tool call is real and codebase-relevant.** The standard failure shape: task A checks "is session X expired?", unlocks, task B (a `click` call) looks up session X and starts using the `Page`, then task A's eviction step removes/closes session X out from under B — not a memory-safety bug (Rust's ownership prevents UB) but a logical use-after-remove: B's in-flight CDP call now targets a closed page. The idiomatic tokio-safe fix is to make "check-expiry-and-evict-or-return-handle" a **single critical section** under one lock acquisition (e.g. via `HashMap::entry()`), not two separate `.lock()` calls — and/or store `Arc<Page>` (or an internal `Arc`-wrapped session struct) in the map so a tool call that already holds a strong reference keeps the `Page` alive even if the reaper concurrently removes it from the map; the tool call finishes against the (now-detached) page rather than crashing on a null lookup, and the *next* call correctly gets a "session not found" once the map entry is gone. This directly matches the requirement's called-out rabbit hole: "existing shared-Browser-no-mutex design + new persistent-page-per-session + background reaper = TOCTOU hazards." [tokio Mutex docs](https://docs.rs/tokio/latest/tokio/sync/struct.Mutex.html), [tokio shared-state tutorial](https://tokio.rs/tokio/tutorial/shared-state)
- **A panicking reaper task does not take down the daemon by default** — tokio catches panics in spawned tasks and reports them as an `Err` on the `JoinHandle`, so the process survives. The actual risk is the opposite of "daemon crashes": if nobody `.await`s the reaper's `JoinHandle` (and per `stack.md`'s pattern for the existing CDP event-drain task, this codebase's convention is to spawn-and-drop the handle), a reaper panic is **silently swallowed** — the reaper simply stops running forever with no daemon-visible signal, and sessions accumulate unbounded from that point on (a slow memory leak that looks like "it worked in testing" but degrades in long-running production). Mitigation: either wrap the reaper's loop body in `catch_unwind`-safe per-iteration error handling (so one bad iteration doesn't kill the loop) or have the reaper log a metric/warning on each pass so an unexpected stop is externally observable. [tokio JoinHandle docs](https://docs.rs/tokio/latest/tokio/task/struct.JoinHandle.html)
- **A dropped `JoinHandle` detaches rather than cancels** (tokio's documented "detach on drop" semantics, matching `std::thread::JoinHandle`) — this is actually the *opposite* of the "reaper leaks/blocks shutdown" risk named in requirements.md: the reaper task will keep running forever in the background unless something explicitly signals it to stop (e.g. a `CancellationToken` or a shutdown channel checked each loop iteration). Requirements.md's "must not leak or block daemon shutdown" concern needs both: (a) don't let the reaper block shutdown (it won't, since spawn+drop doesn't await it) and (b) don't let the reaper leak *forever after* shutdown starts (it will, unless explicitly cancelled) — the fix is a `tokio::select!` between the reaper's sleep/tick and a shutdown signal, with an explicit `.abort()` or cancellation-token check, not just spawn-and-forget like the existing CDP-drain task at `crates/native/src/browser.rs:27`.

## 4. Security/safety pitfalls — SSRF and beyond

- **`a15ed28` (SSRF guard for crawler seed/link URLs) established the pattern this feature should reuse, and its own documented limitation matters more here than there.** The guard (`crates/core/src/tools/webcrawl.rs`, `blocked_host_reason`/`NetworkPolicy`) blocks IP-literal loopback/private/link-local addresses and `localhost`-family hostnames before `read_website`/`download_website` fetch a URL, gated by `NetworkPolicy::Enforce` vs. an env-var-only bypass never exposed on tool-call input. The commit message explicitly documents: *"this is a pre-fetch literal check only ... it doesn't catch DNS rebinding or a redirect followed internally."* **`navigate` should call the same `blocked_host_reason` check** before loading a URL into a session-scoped page — there is no reason for a browser-driven fetch to have a materially weaker SSRF posture than the crawler's HTTP fetch, and the reuse is essentially free (same function, same policy plumbing).
- **`click`/`type` reopen the SSRF gap the guard closes, and this is a novel risk beyond what `a15ed28` covers.** The `webcrawl.rs` guard only ever checks a URL immediately before an HTTP/browser fetch call *the caller controls the URL for*. But `click` (submitting a form) or `type` (filling a field that an onchange/onsubmit handler reads) can trigger a same-tab navigation to a URL the guard never sees, because no Rust-side code ever constructs or passes that URL — the browser itself navigates internally in response to page JS, entirely inside the CDP `Page`/`Target` domain. An attacker-controlled page (e.g. reached via a public URL that passes the `navigate`-time check) could embed a form whose `action` or a script's `location.assign()` points at `http://169.254.169.254/` or `http://localhost:PORT/admin`, and clicking a button on that legitimate page would carry the session's already-privileged network position straight past the `navigate`-time guard. **This is the most important pitfall to design against**: an SSRF guard checked only at `navigate` time provides no protection at all for `click`/`type`-triggered in-page navigation, and the requirements' Scope section only lists `navigate`/`click`/`type`/`snapshot` without calling out this asymmetry. Closing it requires either (a) hooking chromiumoxide/playwright's own navigation-started event (CDP `Page.frameNavigated`/`Network.requestWillBeSent`, or Playwright's `page.on('framenavigated')`) and re-running `blocked_host_reason` against *every* navigation the page makes, not just the one Rust explicitly requested, or (b) accepting and documenting the gap as an explicit out-of-scope risk (mirroring `a15ed28`'s "documented limitation" style) rather than silently shipping an SSRF guard that only covers one of the four operations.
- Related, smaller risk: `type` into a field is itself a vector for a prompt-injection-adjacent attack in the other direction — if the *page content* is untrusted and an LLM caller is deciding what to type based on snapshot output, a page can render fake form labels/roles designed to trick the calling agent into typing sensitive data (credentials, tokens visible in the calling context) into an attacker-controlled field. This is a caller-side (agent) risk more than a daemon-side one, but worth a one-line callout in the tool's schema/description since it's specific to LLM-driven `type` calls in a way it wouldn't be for a human using a browser.

## 5. Failure-mode brainstorm — "ships, passes tests, unpleasant in real use"

- **Stale locators after re-navigation.** A `snapshot` taken right after `navigate` hands the caller AX-tree-derived locators (role+name per `stack.md`'s recommended Playwright-style `getByRole` mapping). If the caller's next `click` itself causes a navigation (per §2 above), any *subsequent* locator from the pre-click snapshot is now describing a page that no longer exists — tests that do exactly one navigate→snapshot→click→snapshot cycle will pass easily, but a realistic multi-step task (fill a multi-page form) will hit "locator not found" or, worse, silently match a *different* element that happens to share the same role+name on the new page. Design implication: locators should probably be scoped/invalidated per-navigation (e.g. include a generation/page-version counter) rather than treated as durable identifiers across navigations.
- **Reaper interval too aggressive for realistic multi-step tasks.** An LLM-driven caller doing navigate → snapshot → (think) → click → (think) → type → snapshot can easily have multi-second-to-tens-of-seconds gaps between tool calls (model latency, not page latency). A reaper tuned against "a human clicking every second" assumptions, or tested only with tight-loop synthetic tests, will look correct in CI but will silently kill sessions mid-task in real usage — the failure surfaces as a confusing "session not found" error on the *next* tool call rather than an obvious timeout, and is easy to under-provision for because test suites don't naturally include multi-second thinking gaps.
- **Snapshot output too verbose/unstructured for an LLM caller.** chromiumoxide's raw CDP `getFullAXTree` returns a flat list of `AXNode`s with backend IDs, roles, and property bags that need real structuring work to become useful; playwright-core's `ariaSnapshot()` returns a YAML-ish tree (per `stack.md`) that's more caller-friendly out of the box. If the native and wasm adapters converge on differently-shaped snapshot output (one closer to raw CDP, one closer to Playwright's curated YAML), the port's `PageSnapshot`-equivalent type either has to force a lowest-common-denominator format (losing playwright-core's more useful structure) or the two backends produce meaningfully different tool-call ergonomics depending on which binary/platform is running — a discrepancy that a same-platform test suite will never surface, since CI likely only exercises one adapter per job.
- **Fresh-tab-per-call was implicitly a resource-safety net that persistent sessions remove.** The current one-shot design (`crates/native/src/browser.rs:9-11`, "fresh tab per call") means any bug in cleanup only leaks for the duration of one tool call. Once sessions are long-lived, the same class of bug (e.g. an error path that returns before calling `page.close()`/removing the map entry) leaks for the idle-timeout duration or forever if the reaper itself has the JoinHandle-drop/cancellation issue from §3 — a bug that was invisible/inconsequential under the old model becomes a slow resource leak under the new one, and nothing in a short-lived test run will show this because leaks accumulate over wall-clock time, not test iterations.
