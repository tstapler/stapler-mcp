# Feature Research: browser-automation

## 1. How `@playwright/mcp` designs navigate/click/type/snapshot

- **Refs, not CSS selectors.** `browser_snapshot` returns a YAML-ish accessibility tree where every interactive node gets a `ref` id (e.g. `ref=e5`), like `textbox "Email" [ref=1]`. `browser_click`/`browser_type` take that `ref` (plus a human-readable `element` description used for the LLM's own bookkeeping/logging), not a CSS/XPath selector. [Snapshots docs](https://playwright.dev/mcp/snapshots), [example flow](https://qaskills.sh/blog/playwright-mcp-accessibility-snapshots-reference).
- **Refs are scoped to one snapshot and go stale on any DOM change.** They're only valid until the next navigation or significant re-render; reusing an old ref produces an "element not found"-style error, not a silent wrong-element click. The documented mitigation is simply "take a new snapshot" — there's no server-side staleness detection beyond the element no longer resolving. [Reference](https://qaskills.sh/blog/playwright-mcp-accessibility-snapshots-reference).
- **Actions return a fresh snapshot automatically.** Most tools (`browser_click`, `browser_type`, `browser_navigate`, etc.) return an updated accessibility snapshot as part of their own response, specifically so the caller doesn't need a separate `browser_snapshot` round trip after every action. An open feature request (microsoft/playwright-mcp#1639, June 2026, not yet merged) asks to make these auto-snapshots *inline* in the tool response (they're currently written to a file and referenced) — their own experiment found this cut total tool calls ~40%, explicit snapshot calls ~39%, cost ~26%, and let the model chain up to 13 actions without an observation step. This is strong signal that "return a snapshot with every mutating tool call" is the expected UX, not a nice-to-have.
- **Known/open edge cases from their issue tracker:**
  - **Overlays/portals (dropdowns rendered outside the DOM subtree, e.g. Ant Design/Angular CDK)** are missing from the snapshot entirely — no ref exists, so they're unclickable via the tool ([#1177](https://github.com/microsoft/playwright-mcp/issues/1177)).
  - **Elements missing from the snapshot** in general, with unclear rules about what does/doesn't get accessibility-tree'd ([#514](https://github.com/microsoft/playwright-mcp/issues/514)).
  - **Off-screen/non-viewport elements are included**, which leads agents to try clicking things that aren't actually interactable/visible ([microsoft/playwright#39955](https://github.com/microsoft/playwright/issues/39955)).
  - **Iframes**: the underlying CDP `Accessibility.getFullAXTree` doesn't walk iframe content ([microsoft/playwright#1675](https://github.com/microsoft/playwright/issues/1675)); current playwright-mcp docs describe same-origin iframes being inlined but cross-origin iframes appearing only as an opaque iframe node requiring a separate frame-switch step.
  - **Shadow DOM**: accessibility snapshots don't see inside shadow roots for many component libraries (Shoelace, Lit, etc.) — widely reported as a practical limitation even without a single canonical GitHub issue.
  - **New tabs/popups opened by a click**: playwright-mcp has no way to pre-register a `waitForEvent('page')` listener synchronously the way a raw Playwright script can (each MCP tool call is a discrete request/response). Practically, `browser_click` returns after the *triggering* action, and a separate `browser_tabs` tool call is needed afterward to discover/switch to the new tab. There are open reliability issues around this: repeated failed navigation/install sequences leaving the browser in an "already in use" state ([#1305](https://github.com/microsoft/playwright-mcp/issues/1305)), and a retry loop that spawns multiple stray `about:blank` tabs on `ProcessSingleton`/profile-lock errors ([#1311](https://github.com/microsoft/playwright-mcp/issues/1311)).
  - **Tab cleanup**: closing a tab from the MCP side doesn't always fully release it in the underlying browser/profile ([#1111](https://github.com/microsoft/playwright-mcp/issues/1111)).
  - **Timing/waiting for navigation to settle after a click** isn't exposed as an explicit primitive in the tool surface — it's handled internally by Playwright's own auto-waiting, but agents still routinely need a `browser_wait_for` fallback when a click triggers async content load rather than a full navigation.

## 2. This repo's existing tool patterns

### Input/output schema and error handling — `crates/core/src/tools/fetch.rs`

- One free function per tool (`fetch_page`), generic over the port traits it needs (`<B: BrowserDriver, F: FileStore>`), taking a typed `*Input` struct and returning `Result<*Output, String>`. [crates/core/src/tools/fetch.rs](../../../crates/core/src/tools/fetch.rs).
- **All errors collapse to `String`.** There is no dedicated "user error" vs "internal error" enum at the tool boundary — `PortError` (from `crates/core/src/ports.rs`, variants `Io`/`Timeout`/`Other`) is converted to a plain string with `.map_err(|e| e.to_string())` or wrapped with context (`format!("render {}: {e}", input.url)`). Validation errors (e.g. `"url must not be empty"`) are just `Err(String::from(...))` — same type, same path, as a browser-launch failure or an I/O error.
- **This flows straight through to the MCP layer.** `crates/cli/src/thin_client.rs`'s `#[tool]`-annotated methods return `Result<Json<Output>, String>` directly (e.g. `fetch_page` at line 89-94), and `rmcp`'s `#[tool_router]`/`#[tool_handler]` macros turn an `Err(String)` into an MCP tool-call error response (`isError: true` with the string as message) automatically — there's no custom error-code taxonomy (no distinction like "not found" vs "invalid input" vs "internal") anywhere in the stack. `docs.rs` (`crates/core/src/tools/docs.rs`) follows the identical pattern, including a helper `unknown_source_error(...)` that just builds a formatted `String`.
- **Practical implication for browser-automation**: if `click`/`type`/`snapshot` want to distinguish "session not found" (a normal, retryable condition — the caller should re-navigate) from "internal browser crash," today's codebase has no vocabulary for that distinction at the wire level. The design will either need to (a) follow precedent and just encode it in the error string (e.g. prefix `"session not found: {id}"`) so callers pattern-match on the message, or (b) introduce a new structured error type — which would be a departure from every existing tool in this repo. Given "no fix without root cause" / consistency concerns, (a) matches existing conventions with zero new plumbing; (b) is more correct but touches `ports.rs`, every existing `PortError` call site, and the MCP error mapping.

### Browser adapter shape — `crates/native/src/browser.rs`, `crates/wasm/src/browser.rs`

- `BrowserDriver` (in `crates/core/src/ports.rs:118-128`) currently has exactly one method, `navigate_and_extract(url, timeout) -> Result<PageExtract, PortError>`, explicitly documented as "coarse, call-level" to minimize wasm↔JS boundary crossings.
- **Native adapter is stateless per call today**: `NativeBrowser` holds one shared `chromiumoxide::Browser` for the daemon's whole lifetime and calls `.new_page(url)` fresh on every `navigate_and_extract` — i.e. today there is no persistent `Page` per logical session at all. Session-scoping is a net-new concept, not an extension of an existing map. `Page` methods take `&self` (chromiumoxide is internally-mutable), so a `Mutex<HashMap<SessionId, Page>>`-style registry is workable without needing `&mut self` plumbing through the trait.
- **Wasm adapter delegates to a hand-written JS glue module** (`crates/wasm/src/glue/browser.js`, invoked via `#[wasm_bindgen]` extern "C" declarations) that presumably wraps `playwright-core`. Extending this to session-scoped calls means adding new exported JS functions (`jsNavigate`, `jsClick`, `jsType`, `jsSnapshot`, all keyed by a session id) mirroring the existing `jsNavigateAndExtract`/`jsCloseBrowser` pattern.
- Both adapters already have a `close()`-style lifecycle method called once at daemon shutdown — the idle-timeout reaper for sessions is new machinery, not reuse of an existing timer/cleanup path (no existing background task manages anything time-based today apart from the CDP event-drain loop).

## 3. Edge cases and failure modes the design must explicitly handle

1. **Stale/missing locator on click/type.** Mirrors playwright-mcp's core failure mode: a `ref` (or role+name pair, per this repo's chosen locator scheme) that no longer resolves after a DOM change. Needs a clear, distinguishable error (not swallowed into a generic "click failed").
2. **Session not found** — either because the idle-timeout reaper already closed it, or the caller passed a bad/never-issued `session_id`. Should be a stable, matchable error message/condition so callers can decide to re-`navigate` rather than retry blindly.
3. **`navigate` called again on an existing session** — does it reuse the session's `Page` (in-place navigation, same session_id, refs invalidated) or replace/create a new session? This is unspecified in requirements.md and must be decided; playwright-mcp's own model reuses the current page/tab for `browser_navigate` unless a new tab is explicitly opened.
4. **A click that triggers a new page load or opens a new tab/popup.** Playwright-mcp's own issue tracker shows this is genuinely unsolved territory (stray tabs, "browser already in use" stuck states). The design needs an explicit policy: does the session's `Page` handle stick to the original page even if `window.open`/`target=_blank` fires, or does it silently follow the newest page? Out-of-scope multi-tab support (per requirements.md) makes this sharper — if a click opens a popup and the design has no tab model, that popup either needs to be ignored, auto-closed, or the click result needs to signal "a new context appeared but is not tracked."
5. **Snapshot performance on large/complex pages.** Hand-rolled AX-tree walking over CDP's `Accessibility.getFullAXTree` (native path) has no built-in pagination/depth-limiting; large SPA-heavy pages can produce very large trees. Playwright-mcp's own off-screen-element issue (#39955) shows the naive "walk everything" approach produces noisy, oversized output. Worth deciding upfront whether to cap depth/size or filter to viewport/interactable nodes.
6. **Concurrent tool calls against the same session.** E.g. two `click` calls racing on one `session_id`, or a `snapshot` call racing a `navigate` mid-flight. `chromiumoxide::Page` methods being `&self`-based means concurrent calls are *possible* to issue but not necessarily *safe* to interleave (e.g. a navigate then immediate click risks acting on the pre-navigation page). Needs either per-session serialization (a lock/queue per session) or explicit documentation that callers must serialize their own calls.
7. **Idle-timeout reaper races with an in-flight call.** If the reaper decides to close a session at the same moment a `click` call is using it, the call could fail with a confusing low-level CDP error rather than the clean "session not found" message described in edge case #2. The reaper needs to coordinate with in-flight usage (e.g. touch a last-used timestamp atomically before starting the reaper's closing sweep, or hold the per-session lock from #6 during teardown).
8. **Iframe/shadow-DOM content invisible to the accessibility tree** — same limitation playwright-mcp has; role+name locators simply cannot find content inside shadow roots or (for the native/CDP-based adapter) iframes, since `Accessibility.getFullAXTree` doesn't walk iframes. Should be a documented limitation rather than a silent wrong result.
9. **Timing after click/type — waiting for navigation/async content to settle** before returning a snapshot. Without an explicit wait heuristic, a `click` that triggers navigation may return a snapshot of the pre-navigation (or half-loaded) page.

## 4. Unstated needs beyond the literal requirements

- **`navigate` should almost certainly return an initial snapshot/extract in the same response**, not just a bare `session_id`. Requirements.md already partially captures this ("`navigate`... returns session_id + initial extract/snapshot"), which lines up with playwright-mcp's actual behavior (`browser_navigate` returns the page's snapshot inline) — confirming this is the right call, not scope creep.
- **`click`/`type` returning an updated snapshot automatically is the single highest-leverage design decision**, based directly on playwright-mcp's own measured data (open feature request #1639: ~40% fewer tool calls, ~26% lower cost, longer uninterrupted action chains when actions carry their own post-action snapshot instead of forcing a separate `browser_snapshot` call). Requirements.md doesn't explicitly ask for this, but not doing it would be a regression relative to the tool this feature is explicitly modeled on, and would double the round-trip cost of every action for callers. Strongly recommend `click`/`type` return `{ ok, snapshot }` (or similar) by default rather than requiring a follow-up `snapshot` call.
- **Callers will expect some signal when a click causes a full navigation** (as distinct from an in-page DOM update) — e.g. a `navigated: bool` / `final_url` field alongside the post-action snapshot, so the agent knows refs from the *previous* snapshot are now meaningless without needing to diff URLs itself.
- **A way to know a session was reaped after the fact isn't in scope for an explicit close-session tool, but callers still need to detect it.** Since there's no `close_session` tool and no session-list tool in scope, the *only* signal a caller gets that their session died is a "session not found" error on the next call — this needs to be a distinct, well-documented error (see edge case #2) since it's the sole observability into the reaper's behavior.
