## Concerns

- [ ] **Story 2.1/2.2 (reaper `ClockPort`/`SleepPort` wiring), `crates/native/src/browser.rs` + `crates/cli/src/main.rs`** — Task 2.2.1 defines `spawn_reaper(sessions, clock: impl ClockPort + 'static, sleeper: impl SleepPort + 'static)`, matching `research/architecture.md`'s explicit instruction to drive `last_used` "via the same injected `ClockPort` used elsewhere (`main.rs:91`, `Rc::new(NativeClock)`)" rather than raw `Instant::now()`. But `NativeBrowser::launch()` today (`crates/native/src/browser.rs:17`) takes no arguments, and Task 2.1.1/2.2.2 never add a `clock`/`sleeper` parameter to it or update the `main.rs:83` call site (`NativeBrowser::launch().await`) to pass the existing `Rc::new(NativeClock)` (`main.rs:91`) through. As written, either the reaper falls back to `tokio::time::sleep`/`Instant::now()` directly inside `crates/native` (defensible — native is allowed OS calls — but then Task 2.2.1's `impl SleepPort`/`impl ClockPort` signature and Task 6.1.3's `FakeClock`/`FakeSleeper`-driven unit test have no concrete construction path from `NativeBrowser::launch()`), or `launch()`'s signature must change and no task says so. Remediation: add an explicit task changing `NativeBrowser::launch(clock: Rc<impl ClockPort>, ...)` (or a `with_clock`/setter) and updating `main.rs:83` to pass `clock.clone()`, so Task 6.1.3's fake-driven reaper test is actually wireable against the real construction path.

- [ ] **Task 3.4.2 (`FrameNavigatedGuard`, `crates/native/src/browser.rs`) — illegal-state / stuck-session risk.** The plan sets `BrowserSession.blocked: Option<String>` on a bad frame-navigation event and has every subsequent call check it, but no task specifies clearing `blocked` back to `None` on a later *legitimate* re-navigation of the same session (Task 3.2.1's "re-navigate within existing session" path). If the flag is only ever set and never cleared, a session that briefly bounced through a blocked host (e.g. a redirect chain) becomes permanently unusable even after the caller re-navigates it to a safe URL with `browser_navigate {sessionId}` — directly undercutting the plan's own stated semantics for session reuse (Step 3, "`navigate` session-reuse semantics"). This is a sum-type/illegal-state gap Lens 2 calls out: `blocked` should be reset (or the whole `BrowserSession` should model "blocked" and "navigating" as mutually exclusive states, e.g. an enum) whenever `navigate` is invoked against that session. Remediation: add an explicit sub-task under 3.2.1 or 3.4.2 to clear `blocked = None` at the start of every `navigate` call on an existing session, before the new frame-navigated listener has a chance to re-evaluate the new URL.

- [ ] **Story 2.2/2.3, ordering ambiguity between Task 2.2.1 and Task 2.3.2, `crates/native/src/browser.rs`** — Task 2.2.1 describes the reaper as "closes each such `Page` (`page.close().await`), removes it from the map" (close-then-remove), while Task 2.3.2 requires "session removal in the reaper ... go through a single synchronous `sessions.borrow_mut()` critical section with no `.await` inside it." These two tasks are only mutually consistent if the actual order is *remove-from-map-first* (synchronous, no `.await`), *then* `.await` `page.close()` on the owned, already-detached `Page` — the reverse of how 2.2.1 lists the steps. This is exactly the `RefCell`-borrow-across-`.await` hazard the plan's own Step 0.5(a) names as approach (a)'s core weakness ("enforced by task-level review, not the type system"), so the two tasks describing the same code path in ambiguous/contradictory order is a real risk of the implementer getting it backwards and hitting a runtime `BorrowMutError` (or worse, silently holding a borrow that blocks the next tool call). Remediation: restate Task 2.2.1's step order explicitly as "remove entry from map (sync, no `.await`) → drop borrow → `.await` `page.close()` on the owned `Page`" to match 2.3.2, removing the ambiguity before implementation starts.

- [ ] **Lens 2, item 7 (parse-at-boundary), Story 5.1, `crates/core/src/tools/browser.rs`** — Tasks 5.1.1–5.1.3 describe validating `input.session_id`/`input.ref_id` as non-empty strings and calling "the corresponding `BrowserDriver` method," but never explicitly state the conversion step from the wire-level `String` fields (`BrowserClickInput.session_id: String`, `.ref_id: String`) into the port-level `SessionId`/`Locator` newtypes before the call. This is likely a one-line wrap (`&SessionId(input.session_id)`, `&Locator(input.ref_id)`) and low-risk given both are trivial tuple structs, but leaving the boundary conversion implicit is inconsistent with the plan's own stated rigor elsewhere (e.g. Task 5.1.3 spells out the exact error-message string). Remediation: add the explicit construction to each Story 5.1 task's description so the newtype boundary is a stated, reviewable step rather than an assumed one.

- [ ] **Story 2.3 (Task 2.3.1) long-call edge case, `crates/native/src/browser.rs`** — bumping `last_used` once, synchronously, at call entry (before the `.await`) prevents the reaper from evicting a session for the *common* case, but does not protect a call whose own CDP round-trip legitimately exceeds `SESSION_IDLE_TIMEOUT` (300s) — e.g. a hung `page.goto` on a slow-loading page. In that scenario the reaper would still see a stale `last_used` partway through the call and evict/close the page out from under it, reproducing the exact TOCTOU pitfall.md warns about ("B's in-flight CDP call now targets a closed page"), just with a much longer window than the "instant" case the plan's own AC exercises (10s call vs. 300s timeout). This is a narrow edge case (5-minute single call is unusual) but is the literal scenario `research/pitfalls.md` names as the rabbit hole, so it deserves an explicit call-out rather than being implicitly assumed away by the 10s-call unit test. Remediation: either (a) have long-running calls re-bump `last_used` partway through (e.g. before/after the CDP round trip, not just at entry), or (b) explicitly document this as an accepted residual risk in the plan's Risk Control table (it currently reads as fully mitigated, which overstates the fix).

## Nitpicks

- `AxNode.node_ref: String` (port-level, `ports.rs`) and `Locator(pub String)` wrap the same conceptual value (an opaque snapshot-scoped ref id) but are different types with no conversion helper specified — a `Locator::from(node.node_ref)` or `impl From<&AxNode> for Locator` would tighten the boundary between "ref produced by a snapshot" and "locator accepted by click/type," though `resolve_locator`'s `NotFound` error path already catches any mismatch at runtime, so this is cosmetic, not a correctness gap.
- The `SessionRegistry`/`BrowserSession` types are native-adapter-internal (per `research/architecture.md`, wasm has no Rust-side equivalent) — this asymmetry is fine and consistent with the `Embedder` precedent the plan itself cites, but Step 2's glossary lists `SessionRegistry` without flagging it as native-only the way `Embedder`'s doc comment does for its own asymmetry; a one-line note would keep the glossary as unambiguous as the rest of the plan.
- Pattern selection (Lens 3) is otherwise sound: `Rc<RefCell<HashMap<...>>>` mirrors `SourceLocks` at the right complexity level (no actor/channel over-engineering, no raw `Arc<Mutex<_>>` under-engineering), the AX-tree-walk-as-separate-module (`ax.rs`) keeps single responsibility clean, and the build-vs-buy recommendations (keep `chromiumoxide`, no new crate, thin JS glue against `playwright-core`'s public API) are followed without deviation.
